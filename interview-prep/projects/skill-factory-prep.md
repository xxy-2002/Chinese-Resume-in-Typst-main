# Skill Factory 面试准备

## 一、简历事实

对应简历位置：[2026_6.typ](/home/xxy/Chinese-Resume-in-Typst-main/2026_6.typ:162)

简历里已经写明的事实：

- 这是一个面向业务 `Agent` 的 `Skill` 生产、测评与优化平台
- 借鉴了 `GEPA` 的“轨迹反思 + Genetic-Pareto 候选选择”与 `SkillRL / SkillFoundry` 的闭环思路
- 支持从真实业务 case 中生成、评估、优化可复用 `Skill`
- 设计了可插拔 `Harness`
- 支持 `Executor / Evaluator / Optimizer`
- 管理候选 `Skill`、评测集、指标配置与版本化回归结果
- 基于 `GEPA` 做候选生成与迭代优化
- 构建了 `Skill` 沙盒执行环境
- 记录 `step trace`、`tool call`、标准输出、产物差异、评估打分
- 打通业务 Agent 集成与 case 采集闭环
- 支持批量测评、回归对比与 `Skill` 发布门禁

## 二、这个项目最该讲的价值

这个项目的重点不是“我做了一个 Agent 平台”，而是：

- 把 `Skill` 当成可生产、可评测、可优化、可发布的工程对象
- 把优化过程做成闭环
- 让 `Skill` 的改进不只靠经验，而是能靠 case、轨迹、指标和回归结果来驱动

补充参考材料：

- [aboutskill.md](/home/xxy/Chinese-Resume-in-Typst-main/interview-prep/docs/aboutskill.md)
- [gepa-prep.md](/home/xxy/Chinese-Resume-in-Typst-main/interview-prep/projects/gepa-prep.md)

这份补充材料里最值得吸收的点有两个：

- `Skill` 看起来像 prompt，但工程上更像 `Harness`
- `Skill` 的优化不该只是手工改 prompt，而应该是可迭代、可评测、可回滚、可选优的训练闭环

这里要明确区分：

- `aboutskill.md` 是他人的相关工作与方法参考
- 它和你的项目有相似痛点与相似方向
- 它可以作为你解释设计思路、行业趋势和方法论的参考
- 它不能直接替代你简历里的项目事实

## 三、推荐讲法

建议主线：

1. 为什么要做 `Skill Factory`
2. 一个 `Skill` 从哪里来
3. 怎么执行、怎么评测、怎么优化
4. 为什么需要 sandbox 和 trace
5. 怎么把线上或测试 case 回流进来

可以这样表达：

“Skill Factory 面向的不是单次任务，而是业务 Agent 背后的 Skill 资产。我的核心目标是把 Skill 的生产、评估、优化、回归、发布串成闭环。平台里最关键的是可插拔 Harness，把 Executor、Evaluator、Optimizer 抽出来，让不同任务类型都能落到同一套流程。然后基于执行轨迹、工具调用结果和失败 case，生成新的 prompt/spec/code 候选，再通过多目标指标和 Pareto Frontier 筛选保留更优版本。” 

如果你想讲得更完整，可以再补一句：

“我后来把它进一步抽象成一个 `skill-evolver` 式的训练框架。它不只是跑评测，而是把 `loop + eval + gate + trace` 接成闭环，让 skill 可以围绕真实 case 自己迭代、自己回归、自己选 checkpoint。”

## 四、来自补充材料的可展开机制

### 1. Skill 更像 Harness

这句话很适合当开场：

“Skill 最容易被误解成一段 prompt，但要让它稳定工作，实际是在搭一套 harness。触发边界、安全规则、参考资料一致性、脚本版本兼容、回归验证，这些加起来已经是系统问题，不是写一段提示词的问题。”

### 2. 8 阶段 Loop

可以讲成这样：

- `Setup`：准备 workspace、评测计划、baseline
- `Review`：读取历史结果、trace、失败 case
- `Ideate`：基于 trace 做失败诊断，提出单点改动
- `Modify`：每轮只做一个原子化修改
- `Commit`：先保留审计轨迹
- `Verify`：跑评测
- `Gate`：决定 keep 还是 revert
- `Log / Loop`：记录结果并进入下一轮

适合回答：

- 你的优化闭环是怎么运转的
- 为什么你说它像“训练框架”

### 3. 三层评测

这是补充材料里最适合转成面试表述的一块：

- `L1`：快速结构和安全检查
- `L2`：全量 dev 集评测
- `L3`：holdout 与 regression 校验

可直接说：

“我不是只跑一套总评测，而是按成本和可信度分层。先做快速结构与安全检查，再跑 dev 集评测，最后在关键节点上做 holdout 和 regression，防止只在开发集上变好。”

### 4. 5 维 AND 门控

这个点很加分，因为它体现了工程约束而不是单纯追分。

可讲法：

“每一轮改动不是看单一分数，而是过一组 AND 门控。只有关键维度都满足才保留，否则直接回滚。这样可以避免某一项指标变好，但成本、稳定性或者回归风险变坏。”

### 5. Trace 诊断

这个点和你的简历经历非常一致。

可讲法：

“核心不是只看总分，而是保留原始执行 trace。这样下一轮优化不是拍脑袋改，而是基于具体 case、具体工具调用和具体失败路径做诊断，知道为什么错、该改哪里、改完应该影响什么。”

## 六、面试官最可能追问的点

- 为什么 `Harness` 要可插拔
- `Executor / Evaluator / Optimizer` 分别负责什么
- `GEPA` 在你的系统里具体怎么落地
- 为什么要做 `Pareto Frontier`
- 为什么说 `Skill` 更像 `Harness`
- `8 阶段 Loop` 里最关键的是哪一步
- 为什么要分 `L1 / L2 / L3` 三层评测
- 为什么要做 `AND` 门控，而不是加权打分
- 为什么 `trace` 比摘要或总分更重要
- sandbox 具体隔离了哪些资源
- trace 记录什么，为什么重要
- 发布门禁怎么定义
- 这个项目和你实习里的平台经验有什么联系

## 七、简单回答方向

- `Harness`：
  统一不同任务类型的执行和评测接口，降低平台耦合

- `Evaluator`：
  不只是打一个总分，还要保留细粒度指标，支撑后续优化判断

- `GEPA`：
  利用执行轨迹和 badcase 做候选生成，再通过多指标比较选择更优方案

- `Pareto Frontier`：
  避免只盯一个分数，兼顾成功率、成本、稳定性等目标

- `sandbox`：
  控制文件、网络、依赖和超时，保证执行安全且结果可复现

- `trace`：
  让失败能被复现，让优化前后能被比较

- `三层评测`：
  先用低成本规则快速淘汰明显坏改动，再用 dev 集评测效果，最后用 holdout 和 regression 防止过拟合和回归

- `AND 门控`：
  不允许拿一个维度的提升去掩盖另一个维度的退化

- `trace 优先`：
  优化应当基于证据，不应基于感觉

## 八、你可以主动建立的关联

这个项目和实习经历可以连起来讲：

- 在实习里你接触了 `Agent` 平台、记忆、路由、评估、trace
- 在这个项目里你把这些工程经验收束到 `Skill` 闭环优化上
- 所以它不是孤立项目，而是你过往方向的自然延展
