## 一、消息与异步中间件

### Q01：为什么要引入消息队列？它解决不了什么？

**答案：**

消息队列用于异步解耦、削峰填谷、事件广播和失败重试。生产者不必同步等待所有消费者，消费者可以独立扩展。

它不能凭空提高总处理能力，也不能自动保证跨系统一致性；队列会引入延迟、重复、乱序、积压和运维成本。必须定义消息模型、确认、幂等、重试和堆积告警。

**Key words:** 消息队列、异步、解耦、削峰、事件广播、重复、乱序、积压、幂等

### Q02：至少一次投递如何做到不丢数据？为什么必须幂等？

**答案：**

消费者处理成功后再 ACK；未 ACK 的消息可重投，因此是至少一次而不是不重复。生产者要确认发送结果，消费者要把业务状态和去重记录持久化。

常用做法是业务唯一键、去重表、条件更新、事务外盒和死信队列。外部副作用如扣款、发货要使用幂等接口，不能把“消息只投递一次”当作现实前提。

**Key words:** 至少一次、ACK、重投、去重、唯一键、事务外盒、死信、幂等

### Q03：如何保证分区内有序？全局有序为什么昂贵？

**答案：**

把同一业务实体的消息按稳定 key 路由到同一分区/队列，并让消费者按分区顺序处理。全局有序要求单分区或中心化排序，会牺牲并发和可用性。

重试、并行消费者和跨分区聚合都可能破坏业务顺序；真正需要的通常是“同一订单/用户有序”，而不是全局有序。

**Key words:** 分区、路由 key、局部有序、全局有序、消费者并行、顺序语义

### Q04：Kafka、RabbitMQ 等消息系统怎么选？

**答案：**

Kafka 更偏高吞吐、持久化日志、分区消费和事件回放；RabbitMQ 更偏灵活路由、确认、队列语义和传统任务分发。选择要看吞吐、延迟、顺序、回放、路由、运维和团队经验。

无论选哪种，都要评估副本、磁盘、网络、消费积压、监控、版本升级和跨地域容灾，不能只比较单次 benchmark。

**Key words:** Kafka、RabbitMQ、吞吐、持久化日志、分区、路由、回放、副本、积压

### Q05：消息重试、死信和毒消息如何设计？

**答案：**

把可恢复错误和永久错误区分开；可恢复错误使用指数退避、最大次数和重试队列，超过上限进入死信。毒消息要隔离，避免持续失败阻塞正常消息。

死信必须可查询、可人工修复和安全重放；修复前先检查幂等键和消费者版本，防止重复副作用。

**Key words:** 重试、退避、永久错误、毒消息、死信队列、人工修复、重放、消费者版本

### Q06：数据库写成功但消息发送失败，如何处理？

**答案：**

不要在两个独立系统之间假设一个普通事务能原子提交。可以使用事务外盒：同一数据库事务写业务表和 outbox 事件，再由可靠发布器投递消息并记录状态。

消费者仍需幂等，发布器要扫描未发送事件并重试；也可使用 CDC，但要处理顺序、延迟和 schema 兼容。

**Key words:** 事务外盒、outbox、CDC、发布器、最终一致、重试、schema 兼容

## 二、搜索、存储与平台组件

### Q07：什么时候使用 Elasticsearch，什么时候直接用 MySQL？

**答案：**

MySQL 适合事务、关系约束和精确查询；Elasticsearch 适合全文检索、倒排索引、相关性排序和聚合。搜索索引通常是从数据库异步构建的派生数据，不应默认替代事务真相。

要设计索引更新、删除、重建、版本和延迟；搜索结果不一致时能从数据库或事件日志修复。

**Key words:** Elasticsearch、倒排索引、全文检索、相关性、聚合、派生数据、重建、最终一致

### Q08：对象存储适合放什么？如何保证上传可靠？

**答案：**

对象存储适合图片、模型文件、导出结果和大附件，不适合频繁小事务更新。客户端可使用预签名 URL 直传，服务端只保存对象 key、大小、哈希和业务元数据。

大文件使用分片上传和断点续传；完成后校验 hash，失败分片可重试，生命周期规则负责过期清理，权限采用最小范围。

**Key words:** 对象存储、预签名 URL、分片上传、断点续传、hash、生命周期、最小权限

### Q09：向量数据库/Milvus 在 RAG 中处于什么位置？

**答案：**

向量库保存 embedding、元数据和索引，负责相似度召回；它不是完整 RAG，也不是业务事实数据库。在线链路通常还需要查询改写、过滤、重排、上下文拼装和模型生成。

要关注向量维度、索引类型、召回率、过滤条件、数据更新、删除一致性、冷热分层和索引重建成本。

**Key words:** 向量数据库、Milvus、embedding、相似度召回、元数据、过滤、重排、索引重建

### Q10：连接池和线程池为什么要有上限？

**答案：**

池化可以复用连接和执行资源，减少创建成本；但无上限会把流量传递给下游，最终耗尽文件描述符、线程、数据库连接或内存。

要设置最大连接/线程、队列长度、获取超时、空闲回收和优雅关闭，并通过指标观察池利用率、等待时间和拒绝数。池大小应按下游容量和延迟预算压测得出。

**Key words:** 连接池、线程池、资源上限、队列、获取超时、文件描述符、下游容量、拒绝

### Q11：配置中心和服务发现解决什么问题？配置如何变更？

**答案：**

服务发现提供实例地址、健康状态和版本；配置中心集中管理非代码配置并支持动态更新。两者都不能替代本地默认值、启动校验和故障降级。

配置变更应版本化、审计、灰度和可回滚；密钥不应以明文提交代码或日志，更新失败要保留上一个有效版本。

**Key words:** 配置中心、服务发现、健康状态、版本、灰度、回滚、审计、密钥

### Q12：Nginx、网关和应用服务如何分层？

**答案：**

Nginx/网关负责 TLS 终止、路由、限流、静态资源、认证前置和负载均衡；应用服务负责领域逻辑和数据访问。边界层应设置请求体、连接、读取和上游超时。

网关不能吞掉 trace、错误原因和取消信号，也不能把所有业务重试放在入口层，否则会放大流量。

**Key words:** Nginx、API 网关、TLS 终止、路由、限流、负载均衡、超时、trace

## 三、部署、交付与运维

### Q13：Docker 镜像、容器、Volume 和网络分别是什么？

**答案：**

镜像是分层、不可变的打包产物；容器是镜像运行时的隔离进程；Volume 提供独立于容器生命周期的持久数据；容器网络提供服务间连通和名称解析。

镜像应固定基础版本、最小化层和权限，容器内进程用非 root 用户并处理 SIGTERM；日志和数据不要依赖容器可写层。

**Key words:** Docker、镜像、容器、分层、Volume、网络、非 root、SIGTERM、持久化

### Q14：Kubernetes 部署一个服务要考虑哪些对象？

**答案：**

Deployment 管理副本和滚动更新，Service 提供稳定访问，ConfigMap/Secret 注入配置，Ingress 或网关承接外部流量，探针决定是否接收流量和是否重启。

要设置资源 requests/limits、优雅终止、Pod 反亲和、HPA、PDB 和日志/指标采集。探针只检查进程活着不够，还要区分存活、就绪和依赖可用。

**Key words:** Kubernetes、Deployment、Service、ConfigMap、Secret、Ingress、探针、HPA、PDB

### Q15：CI/CD 流水线如何保证可回滚？

**答案：**

流水线至少包含格式/静态检查、单元测试、构建镜像、依赖和漏洞扫描、集成测试、部署、健康检查和发布门禁。产物要可追溯，使用 commit/tag 与配置版本绑定。

采用滚动、蓝绿或金丝雀发布；数据库变更遵循向前兼容，应用失败时可以回滚代码，数据迁移则使用补偿或反向迁移方案。

**Key words:** CI/CD、静态检查、测试、镜像扫描、产物追溯、金丝雀、健康检查、回滚、schema

### Q16：Git 分支、rebase 和 code review 怎么服务于工程质量？

**答案：**

分支策略应匹配发布频率和团队规模；小而频繁的提交便于审查和回滚，rebase 主要用于整理个人分支历史，合并共享分支前要尊重他人提交。

Review 关注行为变化、边界、测试、迁移和观测，不只看格式。高风险变更应拆分、补回归测试、记录决策和回滚方式。

**Key words:** Git、分支、rebase、提交、code review、回滚、回归测试、变更风险

### Q17：Linux 服务上线后常看哪些指标和命令类别？

**答案：**

先看进程/线程、CPU、内存、文件描述符、磁盘、网络和端口监听，再看应用日志、连接池、队列、GC、慢请求和错误率。命令选择要服务于假设，而不是盲目执行。

常见排查路径是：进程是否存在 → 端口是否监听 → TCP 是否建立 → 请求是否进入应用 → 哪一步耗时/失败。生产环境命令要控制权限、输出量和敏感信息。

**Key words:** Linux、进程、CPU、内存、文件描述符、磁盘、端口、TCP、日志、队列

### Q18：优雅启动和优雅关闭为什么重要？

**答案：**

启动时先加载配置、依赖和路由，再通过就绪检查接收流量；关闭时停止接收新请求，等待在途请求、消费任务和连接排空，最后关闭线程池、连接池和文件。

关闭必须有截止时间，超时后取消或强制终止；消息消费者要先停止拉取再处理完已领取消息，避免重复和半写入。

**Key words:** 优雅启动、优雅关闭、就绪检查、SIGTERM、排空、截止时间、消费者、在途请求

## 四、工程质量与 Agent 落地

### Q19：测试金字塔如何应用到后端服务？

**答案：**

单元测试数量最多、反馈快；集成测试验证数据库、缓存、消息和外部契约；少量端到端测试覆盖关键用户流程。高风险并发、重试、超时、幂等和迁移要有针对性测试。

测试数据和环境要可重复，失败时保留日志/trace；不要用大量脆弱端到端测试替代清晰的单元和契约测试。

**Key words:** 测试金字塔、单元测试、集成测试、端到端、契约测试、并发、幂等、可重复

### Q20：如何定义超时、重试和取消的边界？

**答案：**

为每个调用设置连接、读取和总 deadline，把剩余时间传给下游；只对临时错误重试，并设置次数、退避和抖动。收到取消后停止新工作、释放资源并向上游返回可识别错误。

重试必须考虑业务幂等和流量放大；长链路要有总预算，不能每层都重新开始一个完整超时。

**Key words:** deadline、连接超时、读取超时、总超时、重试、退避、取消、流量放大

### Q21：Prometheus、OpenTelemetry、日志和告警如何配合？

**答案：**

Prometheus 类指标适合趋势和阈值，OpenTelemetry trace 连接跨服务调用，结构化日志记录具体上下文。三者用 trace ID、服务名、版本和时间统一关联。

告警应面向用户影响和 SLO，控制高基数标签与采样；敏感数据脱敏，保留排障所需的最小信息。

**Key words:** Prometheus、OpenTelemetry、指标、Trace、结构化日志、trace ID、SLO、采样、脱敏

### Q22：模型服务如何做网关化和成本控制？

**答案：**

模型网关统一鉴权、模型路由、限流、配额、超时、重试、缓存和审计；根据任务选择本地模型、托管模型或 vLLM/Ollama 等运行方式。

成本指标至少包含输入/输出 token、首 token 延迟、总延迟、并发、失败重试和缓存命中；模型降级要保证输出契约和安全策略不变。

**Key words:** 模型网关、路由、配额、限流、vLLM、Ollama、token、首 token、成本、降级

### Q23：流式 Agent 接口的工程难点是什么？

**答案：**

SSE/WebSocket 只负责传输，业务还要定义事件类型、序号、状态、心跳、取消和断线恢复。模型文本、工具调用、进度和错误应使用可解析的结构化事件。

代理和负载均衡要允许长连接；服务端必须在客户端断开后停止模型和工具任务，并记录完整 trace，避免后台任务继续消耗资源。

**Key words:** SSE、WebSocket、事件类型、序号、心跳、取消、断线恢复、长连接、trace

### Q24：Agent 工具、文件和命令执行如何做隔离？

**答案：**

把模型输出当作不可信输入，工具按白名单暴露 schema、权限和资源上限；文件和命令在 sandbox/workspace 内执行，限制路径、网络、CPU、内存和时长，危险操作需人工确认。

每次调用记录参数摘要、结果、权限判定和 trace；失败可重试但必须先判断副作用和幂等性。

**Key words:** Agent、工具、schema、白名单、sandbox、workspace、资源上限、人工确认、审计

### Q25：线上事故如何处理并形成改进闭环？

**答案：**

先止血：限流、降级、回滚或隔离故障域；再确认影响范围、时间线和用户症状；恢复后用日志、指标和 trace 定位根因。沟通中给出负责人、下一更新时间和预计影响。

复盘不归责个人，而是补监控、测试、容量、权限、文档和自动化修复，并把事故样例加入回归集。

**Key words:** 事故响应、止血、限流、降级、回滚、影响范围、时间线、根因、复盘、回归集
