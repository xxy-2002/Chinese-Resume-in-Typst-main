# 分布式与高可用面试题·融合精简版

> 基于四维框架：**服务发现、服务一致性、服务状态、服务通信**
> 两大分类：**业务系统分布式** vs **数据计算分布式**
> 覆盖：K8s、AWS 多实例、Spark、Flink、Ray

---

## 核心框架：分布式系统四维图谱

| 维度 | 核心问题 | 业务分布式 | 数据计算分布式 |
|------|----------|------------|----------------|
| 服务发现 | 节点怎么找到彼此？ | 服务注册与发现（注册中心） | 资源调度与任务分配（Master-Worker） |
| 服务一致性 | 数据怎么保持正确？ | CAP、分布式事务、分布式锁 | Exactly-Once、容错恢复、副本一致性 |
| 服务状态 | 数据存在哪？ | 无状态外置 / 有状态管理 | 状态后端 / 数据分片 / 中间状态 |
| 服务通信 | 节点间怎么高效交互？ | 同步 RPC + 异步 MQ | Shuffle + 数据本地性 + 通信优化 |

一句话总结：**业务分布式解决"多个人协同服务一个用户"，数据计算分布式解决"多个人协同处理一堆数据"**。

## 一、服务发现

### Q01：服务发现的核心机制是什么？

**答案：**

服务发现解决"节点怎么找到彼此"的问题，核心是**注册 + 心跳 + 查询**。

业务系统：服务实例启动时向注册中心注册自身地址和端口，通过心跳维持存活，客户端或负载均衡器查询注册中心获取目标实例地址。

数据计算系统：Worker 节点向 Master 注册自己的资源（CPU/内存）和任务能力，Master 根据数据本地性原则将任务调度到最近的 Worker。

**Key words:** 注册、心跳、健康检查、元数据、客户端发现、服务端发现

---

### Q02：常见服务注册中心怎么选？

**答案：**

| 注册中心 | 一致性 | 特点 | 适用场景 |
|----------|--------|------|----------|
| ZooKeeper | CP | 强一致，Leader 选举 | 传统 Dubbo 体系 |
| Eureka | AP | 高可用，自身集群 | Spring Cloud |
| Nacos | 可切换 | CP/AP 切换 + 配置中心 | 微服务 + 云原生 |
| etcd | CP | Raft 协议，高性能 | K8s、Service Mesh |
| Consul | CP | 支持多数据中心 | 服务发现 + 配置 |

**选择依据：** 如果必须保证强一致性选 CP（ZooKeeper/etcd/Consul）；如果优先保证可用性选 AP（Eureka）；如果需要配置管理选 Nacos/Consul。

**Key words:** CAP、CP、AP、注册中心、ZooKeeper、etcd、Nacos、Eureka、Consul

---

### Q03：K8s 的服务发现机制是什么？

**答案：**

K8s 提供两层服务发现：

1. **集群内发现**：CoreDNS 将 Service 的 DNS 名称（如 `my-svc.my-namespace.svc.cluster.local`）解析为 ClusterIP；kube-proxy 通过 iptables/IPVS 规则将 ClusterIP 的请求转发到后端 Pod
2. **外部发现**：Ingress（L7 路由）、LoadBalancer 类型 Service（云厂商 ELB）、NodePort（节点端口暴露）

Service 通过 Label Selector 匹配 Pod，Endpoints 控制器自动维护 Service 与 Pod 的映射关系。

**Key words:** CoreDNS、kube-proxy、ClusterIP、Endpoints、Label Selector、Ingress、LoadBalancer

---

### Q04：数据计算框架里的服务发现有什么特点？

**答案：**

数据计算框架的服务发现更关注**资源调度和数据本地性**：

- Spark：Cluster Manager（YARN/Standalone/K8s）负责 Worker 注册，Driver 通过 RPC 获取 Executor 地址
- Flink：JobManager 负责 TaskManager 注册和任务调度，ResourceManager 管理 Task Slot
- Ray：GCS（全局控制服务）保存任务表、对象表、Actor 表和心跳信息，Raylet 负责本地资源管理

核心原则是**数据本地性（Data Locality）**：PROCESS_LOCAL > NODE_LOCAL > RACK_LOCAL > ANY，让计算靠近数据执行，减少网络传输。

**Key words:** 数据本地性、Cluster Manager、JobManager、GCS、Raylet、Task Slot

---

### Q05：AWS 多实例架构的服务发现怎么做？

**答案：**

AWS 的服务发现是云原生的三层模型：

1. **DNS 层**：Route 53 提供域名解析、健康检查和故障转移
2. **负载均衡层**：ELB（经典）/ ALB（L7 HTTP）/ NLB（L4 TCP）作为统一入口，自动感知后端 EC2 实例的健康状态
3. **应用层**：Auto Scaling 组根据指标自动扩缩容实例，ELB 自动将新实例加入流量分发

**Key words:** Route 53、ELB、ALB、NLB、Auto Scaling、健康检查、故障转移

---

### Q06：负载均衡算法有哪些？

**答案：**

| 算法 | 特点 | 适用场景 |
|------|------|----------|
| 轮询（Round Robin） | 均匀分配，无状态 | 实例性能相近 |
| 加权轮询 | 按实例能力分配权重 | 实例配置不同 |
| 最少连接 | 优先分配给连接数最少的实例 | 长连接场景 |
| IP 哈希 | 同一 IP 始终路由到同一实例 | 会话保持 |
| 一致性哈希 | 扩容缩容时只影响部分数据 | 缓存、分布式存储 |

**一致性哈希的核心优势：** 通过虚拟节点解决数据倾斜，扩容/缩容时只需要迁移少量数据，是分布式存储和缓存的核心算法。

**Key words:** 轮询、加权、最少连接、IP 哈希、一致性哈希、虚拟节点、数据倾斜

## 二、服务一致性

### Q07：CAP 定理是什么？工程中怎么选？

**答案：**

CAP 定理：分布式系统最多同时满足**一致性（C）**、**可用性（A）**、**分区容错性（P）** 中的两个。由于网络分区（P）不可避免，工程中必须在 C 和 A 之间取舍。

| 类型 | 保证 | 代表系统 | 取舍原因 |
|------|------|----------|----------|
| **CP** | 强一致 | ZooKeeper、etcd、HBase | 金融、支付、配置中心 |
| **AP** | 高可用 | Eureka、Cassandra、DynamoDB | 互联网应用、社交网络 |

**工程实践：** P 必须保证（网络一定会分区），所以是 C 还是 A 的选择。核心交易系统选 CP（宁可不可用也不能错），用户访问类系统选 AP（宁可数据短暂不一致也不能不可用）。

**Key words:** CAP、C、A、P、分区容错、CP、AP、BASE、最终一致

---

### Q08：BASE 理论是什么？和 CAP 什么关系？

**答案：**

BASE 是 CAP 中选择 AP 后的工程实践：

- **Basically Available（基本可用）**：系统在故障时允许损失部分可用性（如响应时间变长、降级服务）
- **Soft State（软状态）**：允许系统中的数据存在中间状态，且该中间状态不影响整体可用性
- **Eventually Consistent（最终一致）**：系统中的数据副本经过一段时间后最终达到一致

BASE 的本质是**牺牲强一致性换高可用**，是 AP 系统在工程中的落地范式。

**Key words:** 基本可用、软状态、最终一致、牺牲强一致

---

### Q09：分布式事务有哪些方案？各自优缺点？

**答案：**

| 方案 | 一致性 | 特点 | 适用场景 |
|------|--------|------|----------|
| **2PC/3PC** | 强一致 | 阻塞式，同步阻塞，性能差 | 传统数据库XA事务 |
| **TCC** | 最终一致 | 应用层补偿Try-Confirm-Cancel | 金融交易、订单 |
| **Saga** | 最终一致 | 长事务补偿，正向+逆向操作 | 电商下单、订票 |
| **本地消息表** | 最终一致 | 利用数据库事务保证消息先落库 | 订单+消息一致性 |
| **MQ 事务消息** | 最终一致 | RocketMQ 支持，半消息+确认 | 交易系统 |
| **最大努力通知** | 最终一致 | 多次通知不管成功 | 支付回调 |

**选型建议：** 核心交易选 TCC/Saga；简单场景选本地消息表/MQ 事务消息；对性能要求高且能容忍不一致选最终一致。

**Key words:** 2PC、TCC、Saga、本地消息表、MQ事务消息、补偿、幂等

### Q10：分布式锁怎么实现？

**答案：**

| 实现方式 | 核心命令 | 特点 | 问题 |
|----------|----------|------|------|
| Redis SETNX | SET key value NX PX | 高性能，简单 | 看门狗续期、锁过期问题 |
| ZooKeeper | 临时顺序节点 | 自动释放，可重入 | 性能较低 |

**Redis 分布式锁的正确实现：**

1. 加锁：`SET lock_key unique_value NX PX 30000`（NX 保证互斥，PX 设置过期时间）
2. 续期：看门狗（Watchdog）每 10s 自动延长过期时间
3. 解锁：Lua 脚本保证原子性 `if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) end`

**核心问题：** 锁过期（业务没执行完锁就到期）、死锁、误删（A加了锁，过期后B加了锁，A释放了B的锁）。

**Key words:** SETNX、Lua、原子性、看门狗、过期时间、临时顺序节点、RedLock

---

### Q11：共识算法 Raft 是怎么回事？

**答案：**

Raft 解决分布式系统中多个节点如何对日志达成一致的问题，核心包含三个阶段：

1. **Leader 选举**：节点启动时是 Follower，超时未收到心跳成为 Candidate，发起投票，获得多数票成为 Leader
2. **日志复制**：Leader 接收客户端请求，将日志复制到 Follower，Follower 确认后 Leader 提交
3. **安全性**：Leader 选举保证"Leader 包含所有已提交日志"（选举限制）

**Raft vs Paxos：** Raft 更易理解和实现，通过 Leader 统一管理日志复制；Paxos 更抽象，性能在某些场景下更优。工程中常用 Raft（etcd、ZooKeeper 2.0+）或 Raft 变体。

**Key words:** Leader 选举、日志复制、Follower、Candidate、选举限制、安全性、Paxos

---

### Q12：Flink 的 Exactly-Once 怎么保证？

**答案：**

Flink 通过 **Checkpoint + 两阶段提交** 实现端到端精确一次：

1. **Checkpoint**：基于 Chandy-Lamport 算法的分布式快照。Flink 在数据流中插入 Barrier，Barrier 对齐时触发快照，将 Operator 状态保存到持久化存储
2. **两阶段提交（2PC）**：Sink 端先预提交（pre-commit），等所有源 Operator 都完成 Checkpoint 后，再正式提交（commit）
3. **故障恢复**：从最近的 Checkpoint 恢复状态，重新处理数据，保证不丢不重

**Key words:** Checkpoint、Barrier、Chandy-Lamport、两阶段提交、Exactly-Once、状态后端

---

### Q13：Spark 的容错机制是什么？

**答案：**

Spark 通过 **RDD Lineage（血缘）** 实现容错：

- 每个 RDD 记录它的创建过程（转换操作）和依赖关系
- 某个分区丢失时，根据 Lineage 信息重新计算该分区
- 窄依赖（narrow dependency）可以在 Stage 内 Pipeline 执行，失败时只需重算当前 Stage
- 宽依赖（wide dependency）触发 Shuffle，需要从上游所有分区重新计算
- **Checkpoint** 切断长血缘，将中间结果写入 HDFS，防止 lineage 过长导致重算成本太高

**Key words:** RDD、Lineage、血缘、窄依赖、宽依赖、Shuffle、Checkpoint、DAGScheduler

---

### Q14：Kafka 如何保证消息不丢？

**答案：**

Kafka 通过多层机制保证消息不丢：

1. **Producer 端**：`acks=all` 确保所有 ISR 副本都写入成功；`retries=MAX` 无限重试；启用 `idempotence=true` 防止重试导致重复
2. **Broker 端**：`min.insync.replicas=2` 确保至少有 2 个副本成功写入；日志先写 PageCache 再刷盘（顺序写）；副本同步机制（ISR）
3. **Consumer 端**：手动提交 offset，确保消息处理完再提交；幂等处理防止重复消费
4. **`__consumer_offsets`**：副本数必须设为 3，否则存 offset 的 Broker 挂了所有消费者停摆

**Key words:** acks=all、ISN、min.insync.replicas、幂等、offset、PageCache、顺序写

---

### Q15：Kafka 挂了怎么恢复？

**答案：**

1. **Broker 宕机**：Controller 通过心跳检测失效（超过 session.timeout.ms），从 ISR 中选举新 Leader（优先 broker.id 最小的），客户端自动重连新 Leader，宕机节点重启后作为 Follower 追数据
2. **Controller 宕机**：ZooKeeper 架构下其他 Broker 竞争创建 /controller 临时节点；KRaft 架构下基于 Raft 协议选举新 Controller
3. **关键配置**：`unclean.leader.election.enable=false` 禁止非 ISR 副本当选；`offsets.topic.replication.factor=3` 保证 offset 不丢
4. **Consumer 故障**：触发 Rebalance，其他 Consumer 重新分配分区

**Key words:** Controller、ISR、Leader选举、Rebalance、session.timeout、unclean.leader.election

## 三、服务状态

### Q16：无状态设计和有状态设计怎么选？

**答案：**

| 维度 | 无状态 | 有状态 |
|------|--------|--------|
| 定义 | 实例不保存任何业务数据，状态外置 | 实例自身保存业务状态 |
| 扩容 | 直接加副本数，简单 | 需要状态迁移，复杂 |
| 故障恢复 | 重启即恢复，无状态丢失 | 需要从外部恢复状态 |
| 适用 | Web服务、API网关、微服务 | 数据库、缓存、计算引擎 |

**业务系统最佳实践：** 服务层尽量无状态，状态外置到 Redis/数据库。K8s 中 Deployment 管理无状态应用，StatefulSet 管理有状态应用。

**数据计算框架的状态管理：** Flink 用 KeyedState/OperatorState（本地 RocksDB + 增量 Checkpoint）；Spark 用 RDD（天然不可变，无状态计算）；Ray 用 Actor（有状态）和 Task（无状态）。

**Key words:** 无状态、有状态、StatefulSet、Deployment、KeyedState、OperatorState、Actor

---

### Q17：缓存三兄弟（穿透、击穿、雪崩）怎么解决？

**答案：**

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| **穿透** | 查询不存在的数据，绕过缓存直接打数据库 | 布隆过滤器（Bloom Filter）、空值缓存（短期） |
| **击穿** | 热点Key过期瞬间，大量请求打数据库 | 互斥锁（Redis SETNX）、永不过期（逻辑过期） |
| **雪崩** | 大量Key同时过期，数据库压力骤增 | 随机过期时间、多级缓存、限流降级 |

**Cache-Aside 模式：** 读写时先操作缓存，缓存未命中时查数据库并回填缓存。写操作先更新数据库再删除缓存（Cache-Aside Write-Through）。

**Key words:** 穿透、布隆过滤器、击穿、互斥锁、雪崩、随机过期、Cache-Aside

---

### Q18：Flink 的状态后端怎么选？

**答案：**

| 状态后端 | 存储 | 适用场景 | 特点 |
|----------|------|----------|------|
| HashMapStateBackend | JVM 堆内存 | 小状态，测试环境 | 速度快，状态大会 OOM |
| EmbeddedRocksDBStateBackend | 本地磁盘 + 增量 Checkpoint | 生产环境，大状态 | 支持增量 Checkpoint，性能稳定 |
| FsStateBackend | 文件系统 | 中等状态 | 较少使用 |

**增量 Checkpoint：** 只上传自上次 Checkpoint 以来变化的部分，大幅减少存储和网络开销。

**Key words:** HashMapStateBackend、RocksDB、增量Checkpoint、KeyedState、OperatorState

---

### Q19：K8s 的状态管理有哪些核心对象？

**答案：**

| 对象 | 作用 | 状态管理 |
|------|------|----------|
| **Pod** | 最小调度单元 | 包含一个或多个共享网络的容器 |
| **Deployment** | 无状态应用 | 支持滚动更新/回滚，ReplicaSet 管理副本数 |
| **StatefulSet** | 有状态应用 | 稳定网络标识（pod-0、pod-1）+ 持久化存储（PV/PVC） |
| **DaemonSet** | 守护进程 | 每个节点上一个实例 |
| **ConfigMap/Secret** | 配置和密钥 | 与 Pod 解耦，支持动态更新 |
| **PV/PVC** | 持久化存储 | 生命周期独立于 Pod |

**QoS 等级：** Guaranteed（requests == limits）> Burstable > BestEffort，OOM 时按 BestEffort → Burstable → Guaranteed 顺序驱逐。

**Key words:** Pod、Deployment、StatefulSet、DaemonSet、ConfigMap、PV/PVC、QoS、HPA

## 四、服务通信

### Q20：同步通信和异步通信怎么选？

**答案：**

| 维度 | 同步通信（RPC/HTTP） | 异步通信（消息队列） |
|------|---------------------|---------------------|
| 延迟 | 低（毫秒级） | 高（取决于消费速度） |
| 耦合度 | 高（调用方依赖被调用方） | 低（解耦） |
| 吞吐量 | 低 | 高 |
| 适用场景 | 实时查询、交易下单 | 异步处理、事件通知、削峰 |
| 容错 | 需要超时重试 | 消息持久化，重试简单 |

**原则：** 需要实时响应的用同步（RPC），需要解耦和削峰的用异步（MQ）。实际系统两者结合：同步核心链路 + 异步非核心链路。

**Key words:** 同步、异步、RPC、HTTP、消息队列、削峰、解耦、超时重试

---

### Q21：RPC 的核心原理是什么？

**答案：**

RPC（远程过程调用）让本地调用像本地函数一样调用远程服务，核心流程：

1. **客户端**：调用 stub → 序列化参数 → 网络发送
2. **网络层**：通过 TCP/HTTP 传输序列化后的字节流
3. **服务端**：接收字节流 → 反序列化 → 执行实际方法 → 序列化结果 → 返回
4. **客户端**：接收结果 → 反序列化 → 返回给调用方

**核心组件：**
- 序列化：Protobuf（高效）、JSON（可读）、Thrift
- 服务发现：从注册中心获取服务地址列表
- 负载均衡：轮询/加权/一致性哈希
- 熔断降级：Hystrix/Sentinel，故障时快速失败
- 超时重试：设置 deadline，只对临时错误重试

**Key words:** 序列化、Protobuf、服务发现、负载均衡、熔断、降级、限流、超时重试

---

### Q22：Shuffle 是什么？为什么是性能瓶颈？

**答案：**

Shuffle 是分布式计算中 Map 阶段和 Reduce 阶段之间的**数据重分布**过程：

1. Map 阶段完成计算后，将结果按 Key 分区排序写入本地磁盘
2. Reduce 阶段从所有 Map 节点拉取属于自己的分区数据
3. 合并排序后执行 Reduce 逻辑

**为什么是瓶颈：**
- 网络传输量大：所有中间结果都要跨节点传输
- 磁盘 IO：Map 端需要溢写（Spill）到磁盘，Reduce 端需要合并
- 数据倾斜：某些 Key 分配不均导致部分 Reduce 任务耗时很长

**优化手段：**
- Map 端预聚合：reduceByKey 替代 groupByKey，减少 Shuffle 数据量
- Broadcast Join：小表广播到所有节点，避免 Shuffle
- 压缩：Snappy/LZ4 压缩 Shuffle 数据
- 自定义 Partitioner：解决数据倾斜

**Key words:** Shuffle、MapReduce、宽依赖、Spill、数据倾斜、预聚合、Broadcast Join、分区器

---

### Q23：Spark 的通信模型是什么？

**答案：**

Spark 的通信模型基于 **DAGScheduler + TaskScheduler**：

1. **DAGScheduler**：根据宽依赖将 DAG 切分为 Stage（窄依赖内 Pipeline 执行）
2. **TaskScheduler**：将 TaskSet 分配到 Executor 上执行
3. **通信机制**：Netty 异步 NIO，BlockManager 管理内存和磁盘中的数据块
4. **Shuffle**：SortShuffle（默认）或 HashShuffle，宽依赖触发 Shuffle Write + Shuffle Read
5. **广播变量**：大表广播到所有节点，避免重复传输
6. **累加器**：跨 Executor 的聚合计数器

**Key words:** DAGScheduler、TaskScheduler、Stage、Netty、BlockManager、SortShuffle、广播变量、累加器

---

### Q24：Flink 的通信模型是什么？

**答案：**

Flink 的通信模型基于 **Operator Chain + Task Slot**：

1. **Operator Chain**：将多个算子合并到同一线程执行，减少序列化和线程切换开销（类似 Spark 的 Pipeline）
2. **Task Slot**：TaskManager 的资源执行单元，支持 Slot 共享（一个 Slot 运行多个 Operator Chain）
3. **背压（Backpressure）**：下游处理慢导致上游阻塞，通过 Flink UI 监控背压状态
4. **Watermark**：处理乱序事件和迟到数据的时间机制
5. **网络通信**：基于 Netty 的异步数据交换，支持 Pipeline 数据流

**Key words:** Operator Chain、Task Slot、背压、Watermark、Netty、Pipeline

---

### Q25：Ray 的通信模型有什么独特之处？

**答案：**

Ray 的通信模型基于 **共享内存 + 动态 DAG**：

1. **Object Store（Plasma）**：基于共享内存的对象存储，同节点内零拷贝读取不同节点的 Object 通过 GCS 传递引用
2. **ObjectRef（提货单）**：不可变的分布式对象引用，可作为下一个 Task 的参数，自动构建动态 DAG
3. **动态 DAG**：边干边连线，依赖关系由 ObjectRef 参数自动织成，不需要预定义整个 DAG
4. **Work-Stealing 调度**：本地调度器优先，资源不足时转发全局调度器，支持数据本地性优化
5. **Actor 通信**：Actor 的方法调用按顺序执行，通过 GCS 心跳检测 Actor 状态

**Key words:** Plasma、共享内存、ObjectRef、动态DAG、Work-Stealing、GCS、Actor

## 五、K8s 分布式系统深度梳理

### Q26：K8s 的核心架构是什么？

**答案：**

```
┌─────────────────────────────────────────────┐
│              Control Plane（控制平面）        │
│  kube-apiserver  ← 唯一入口，REST API    │
│  etcd            ← 分布式 KV 存储，Raft  │

```

- **Control Plane** 声明期望状态，控制器不断将实际状态调谐到期望状态

### Q27：K8s 的调度机制是什么？

**答案：**

K8s 调度分两步：

1. **过滤（Filtering）**：筛选出满足资源请求、亲和性/反亲和性、污点（Taint）容忍度等条件的节点
2. **打分（Scoring）**：对过滤后的节点打分（资源利用率、负载均衡、亲和性等），选择最优节点

**调度策略：**
- 资源请求：requests（保证最小资源）和 limits（最大资源限制）
- 亲和性：节点亲和（NodeAffinity）、Pod 亲和（PodAffinity）、Pod 反亲和（PodAntiAffinity）
- 污点和容忍：Taint 标记节点，Toleration 允许 Pod 调度到特定节点

**Key words:** 过滤、打分、资源请求、资源限制、亲和性、反亲和、污点、容忍

**Key words:** 多副本、健康检查、HPA、PDB、多节点、Service、Endpoints

## 六、AWS 多实例架构深度梳理

### Q29：AWS 高可用架构的核心模式是什么？

| 模式 | 层级 | 作用 |

| **Multi-AZ** | 应用层和数据库跨多个可用区部署 | 单 AZ 故障不影响服务 |

### Q30：Auto Scaling 的工作原理是什么？

**答案：**

Auto Scaling 基于**指标 + 策略**自动调整 EC2 实例数量：

1. **指标采集**：CPU 利用率、网络流量、请求数、自定义 CloudWatch 指标
2. **触发条件**：设置扩容阈值（如 CPU > 70%）和缩容阈值（如 CPU < 30%）
3. **执行动作**：触发条件时自动创建或终止 EC2 实例
4. **ELB 联动**：新实例自动注册到负载均衡器，终止实例自动从负载均衡器移除
5. **冷却时间**：避免频繁伸缩，设置冷却期（如 300s）

**扩展策略：** 简单策略（基于阈值）、目标追踪（维持目标指标值）、预测性伸缩（基于历史数据预测）

**Key words:** CloudWatch、阈值、扩容、缩容、冷却时间、目标追踪、预测性伸缩、ELB

## 八、Flink 分布式计算深度梳理

### Q33：Flink 的核心抽象是什么？

**答案：**

| 抽象 | 特点 | 适用场景 |
|------|------|----------|
| **DataStream** | 无界数据流，逐条事件驱动 | 实时处理 |
| **DataBatch** | 有界数据流（流的特例） | 批处理 |
| **Window** | 时间窗口（滚动/滑动/会话/全局） | 聚合计算 |
| **Watermark** | 事件时间进度标记，处理乱序事件 | 迟到数据处理 |
| **ProcessFunction** | 低级别 API，支持定时器 | 复杂事件处理 |

**核心编程模型：** DataStream API → Table API → SQL，底层统一执行。

**Key words:** DataStream、DataBatch、Window、Watermark、ProcessFunction、CEP、Table API

---

### Q34：Flink 的 Checkpoint 机制详解？

**答案：**

Checkpoint 是 Flink 容错的核心，基于 Chandy-Lamport 算法：

1. **Barrier 对齐**：Flink 在数据流中插入 Checkpoint Barrier，Barrier 随数据流传播
2. **对齐快照**：当所有输入通道的对齐 Barrier 到达时，Operator 对当前状态做快照
3. **状态存储**：快照保存到持久化存储（HDFS/RocksDB），支持增量 Checkpoint
4. **故障恢复**：从最近的 Checkpoint 恢复所有 Operator 状态，重新消费数据
5. **Exactly-Once**：配合 2PC Sink 保证端到端精确一次

**Savepoint vs Checkpoint：** Checkpoint 自动触发，用于故障恢复；Savepoint 手动触发，用于版本升级、迁移、集群缩容。

**Key words:** Barrier、Chandy-Lamport、对齐快照、增量Checkpoint、Savepoint、Exactly-Once

---

### Q35：Flink 的背压怎么处理？

**答案：**

背压（Backpressure）是下游处理慢导致上游阻塞的现象：

1. **检测**：Flink Web UI 中监控背压状态（OK / LOW / HIGH）
2. **原因**：下游 Operator 处理速度慢、网络带宽不足、数据倾斜
3. **处理**：
   - 增加并行度（扩容）
   - 优化慢 Operator（升级硬件、优化逻辑）
   - 调整 Buffer 数量和网络参数
   - 数据倾斜时调整 Partitioner 或预聚合

**Key words:** 背压、Buffer、并行度、Flink UI、网络带宽、数据倾斜

## 九、Ray 分布式计算深度梳理

### Q36：Ray 的核心抽象是什么？

**答案：**

| 抽象 | 特点 | 适用场景 |
|------|------|----------|
| **Task** | 无状态远程函数（@ray.remote），执行完即结束 | 并行计算 |
| **Actor** | 有状态分布式对象（@ray.remote 装饰类），方法按顺序执行 | 状态管理、强化学习 |
| **Object / ObjectRef** | 不可变分布式对象 + 提货单，自动构建动态 DAG | 数据依赖传递 |
| **Placement Group** | Gang-Scheduling 保证多卡资源原子分配 | 多 GPU 训练 |

**核心特点：** Ray 是**动态 DAG**框架——边干边连线，依赖关系由 ObjectRef 参数自动织成，不同于 Spark/Flink 的预定义 DAG。

**Key words:** Task、Actor、ObjectRef、Placement Group、动态DAG、Ray Train、Ray Tune、Ray Serve、RLlib

---

### Q37：Ray 的 Actor 模型怎么理解？

**答案：**

Ray Actor 是有状态的分布式对象：

1. **定义**：用 @ray.remote 装饰的类，实例化后驻留在某台机器上
2. **执行**：Actor 的方法按顺序执行（同一 Actor 不会并发执行方法），保证状态一致性
3. **状态**：Actor 的属性在其生命周期内持久保留，即使程序重启也可以从 Savepoint 恢复
4. **使用场景**：强化学习中的环境模拟器、大模型推理中的模型实例、超参搜索中的评估器

**与 Task 的区别：** Task 无状态、可并行、失败重试；Actor 有状态、顺序执行、故障后重建。

**Key words:** Actor、@ray.remote、有状态、顺序执行、状态持久化、重建

## 十、框架横向对比

### Q38：Spark vs Flink vs Ray 怎么选？

**答案：**

| 维度 | Spark | Flink | Ray |
|------|-------|-------|-----|
| **定位** | 批处理引擎 | 流处理引擎 | AI 分布式计算 |

| **语言** | Scala/Java/Python | Java/Scala/Python | Python 原生 |

**选型建议：** PB 级离线批处理/SQL 分析 → Spark；低延迟实时流处理/精确一次 → Flink；强化学习/LLM 训练推理/超参搜索 → Ray。

**Key words:** 微批、真流、延迟、容错、状态管理、选型

### Q41：熔断、降级、限流的区别和实现？

**答案：**

| 机制 | 目的 | 实现 | 触发条件 |
|------|------|------|----------|
| **熔断** | 故障隔离，防止级联 | 断路器模式（Closed → Open → Half-Open） | 错误率超过阈值 |
| **降级** | 兜底，保证核心服务 | 返回默认值/简化逻辑/关闭非核心功能 | 系统负载过高/部分服务不可用 |
| **限流** | 保护系统不被压垮 | 令牌桶/漏桶/计数器 | QPS 超过阈值 |

**令牌桶 vs 漏桶：**
- 令牌桶：允许突发流量（桶里有令牌时直接放行），适合有突发流量的场景
- 漏桶：恒定速率流出，平滑流量，适合需要严格限速的场景

**Key words:** 断路器、令牌桶、漏桶、计数器、Half-Open、级联故障

## 十二、高并发核心面试题

### Q43：高并发的核心指标和优化方向？

**答案：**

|------|------|----------|
| **QPS/TPS** | 每秒查询/事务数 | 水平扩容、缓存、异步化 |

1. 缓存：减少数据库访问
2. 异步：非阻塞 IO、事件驱动
3. 并发：多线程/协程、IO 多路复用（epoll）
4. 批处理：合并小请求为大批量
5. 压缩：减少网络传输量
6. 预计算：提前计算好结果
7. 水平扩容：加机器

**Key words:** QPS、RT、P99、吞吐量、缓存、异步、IO多路复用、epoll、水平扩容

### Q44：IO 多路复用（epoll）是什么？

**答案：**

IO 多路复用让单线程可以同时监控多个文件描述符（socket），当某个 fd 就绪时通知程序处理：

1. **select**：遍历所有 fd，有最大数量限制（1024）
2. **poll**：链表存储 fd，无数量限制，但仍然遍历
3. **epoll**：红黑树 + 就绪链表，只返回就绪的 fd，性能最优

**Reactor 模型：** 基于 epoll 的事件驱动模型，事件循环（Event Loop）监听 fd 就绪事件，分发到对应的 Handler 处理。Netty 基于 Reactor 模型实现高性能网络通信。

**Key words:** select、poll、epoll、红黑树、就绪链表、Reactor、Event Loop、Netty

### Q45：零拷贝是什么？

**答案：**

零拷贝（Zero-Copy）指数据在传输过程中不经过用户态缓冲区，直接在内核态完成：

1. **传统方式**：磁盘 → 内核缓冲区 → 用户缓冲区 → 内核 socket 缓冲区 → 网络（4 次数据拷贝）
2. **零拷贝方式**：磁盘 → 内核缓冲区 → 直接发送到网络（DMA 方式，0 次用户态拷贝）

**Kafka 为什么快：** 顺序写（磁盘顺序 IO 比随机 IO 快）+ 零拷贝（sendfile 系统调用）+ PageCache（利用内存缓存热数据）+ 批量发送（聚合小消息为大批量）

**Key words:** DMA、sendfile、PageCache、顺序写、批量、mmap

## 十三、数据管道 vs 业务系统对比

### Q46：业务分布式和数据计算分布式的核心区别？

**答案：**

| 维度 | 业务系统分布式 | 数据计算分布式 |
|------|----------------|----------------|
| **核心目标** | 支撑高并发用户请求，低延迟高可用 | 海量数据高吞吐传输、计算与持久化 |
| **交互模式** | 同步 RPC/HTTP，实时响应 | 异步消息队列/流处理，最终一致 |
| **关注重点** | CAP 权衡、分布式事务、服务治理、幂等 | 数据不丢不重、背压控制、状态管理、Exactly-Once |
| **故障处理** | 熔断降级、超时重试、快速失败 | Checkpoint 恢复、断点续传、重试补偿 |
| **典型组件** | Spring Cloud、Dubbo、Nacos、Seata | Kafka、Flink、Spark、Hadoop、Airflow |
| **一致性** | 核心链路要求强一致 | 大部分接受最终一致，少数需精确一次 |
| **扩展方式** | 按服务维度水平扩容实例 | 按分区/分片维度扩容计算/存储节点 |
| **类比** | 并发编程的升级版（多实例协同） | 并发编程的升级版（多机并行计算） |

**Key words:** 协同、拆分、同步、异步、最终一致、精确一次、水平扩容

### Q47：数据管道的核心架构怎么搭？

**答案：**

数据管道标准分层：

```
数据源 → 数据采集 → 消息队列 → 流/批处理 → 存储 → 展示/服务
```

| 层级 | 选型 | 原因 |
|------|------|------|
| **数据源** | 日志、数据库 CDC、埋点 | 多样化的数据来源 |
| **消息队列** | Kafka | 高吞吐、持久化、分区消费 |
| **流处理** | Flink | 低延迟、Exactly-Once |
| **批处理** | Spark | 大规模离线计算 |
| **存储** | HDFS/Hive、ClickHouse、Elasticsearch | 不同查询场景 |
| **编排** | Airflow/Dagster | 任务调度和依赖管理 |

**Key words:** CDC、消息队列、流处理、批处理、存储、编排、ETL、数据管道
