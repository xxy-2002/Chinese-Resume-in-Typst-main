# 编程语言与工程面试题·融合精简版

> 融合 Python、Go 的语义、容器、并发、内存和服务开发问题。每题末尾都有 **Key words**。

## 一、共同语言语义

### Q01：值语义、引用语义和参数传递怎么讲？

**答案：**

不要简单回答“值传递/引用传递”。更准确的说法是：函数接收的是实参值的绑定；这个值可能是对象引用、指针、结构体副本或 slice/map 的运行时描述。

- 修改共享对象的内容，调用方可能看得到；
- 让形参重新指向另一个对象，通常不影响调用方；
- 是否共享底层存储、谁负责修改、是否需要复制，才是工程上真正要确认的边界。

**Key words:** 值语义、引用、指针、形参绑定、原地修改、底层存储、所有权

### Q02：浅拷贝、深拷贝和不可变对象如何选择？

**答案：**

浅拷贝只复制最外层，嵌套对象仍共享；深拷贝递归复制对象图；不可变对象通过禁止原地修改减少别名问题。

请求上下文、配置快照和跨线程数据要优先明确共享边界。深拷贝不是万能方案，它可能复制很慢、无法复制连接等资源，还可能遇到循环引用。

**Key words:** 浅拷贝、深拷贝、不可变、别名、对象图、上下文隔离、共享状态

### Q03：数组、列表、切片和 tuple 的差异是什么？

**答案：**

数组通常长度固定；列表是可变动态容器；tuple 是不可变序列；Go slice 是“指针、长度、容量”的视图，不等于底层数组本身。

回答时补充四点：是否可变、是否共享底层存储、扩容是否搬迁、并发访问是否安全。slice 截取可能影响原数组，append 后也可能因为扩容而换底层数组。

**Key words:** 数组、list、tuple、slice、len、cap、底层数组、共享、扩容

### Q04：异常、错误返回和资源清理如何设计？

**答案：**

异常适合跨层传播的失败，错误返回适合显式处理的可预期失败。无论采用哪种机制，资源都要在获取后立即注册清理。

文件、连接、锁、事务要覆盖异常路径；错误应保留原因、请求 ID、是否可重试等上下文。重试前必须判断操作是否幂等，否则可能重复扣款或写入。

**Key words:** 异常、错误返回、资源清理、defer、请求 ID、可重试、幂等、事务

### Q05：字符串拼接和内存分配为什么会影响性能？

**答案：**

不可变字符串反复用加号可能重复分配和复制，长循环中可能退化为 O(n²)。Python 可先收集后 join，Go 可用 strings.Builder，字节流可用缓冲区。

优化前先用 profile 或 benchmark 找到热点；同时关注临时对象、序列化和网络拷贝，不能只做语法级替换。

**Key words:** 不可变字符串、重复分配、复制、join、strings.Builder、buffer、benchmark

## 二、Python 语法与运行时

### Q06：Python 是解释型语言吗？is 和 == 有什么区别？

**答案：**

CPython 通常先把源码编译成字节码，再由虚拟机执行；“解释型”是分类上的简化说法。== 比较值，is 比较对象身份。None 这类单例判断适合使用 is None。

**Key words:** CPython、字节码、解释器、对象身份、is、==、None

### Q07：可变默认参数、可变位置参数和关键字参数有什么坑？

**答案：**

函数默认参数在定义时求值，列表和字典会在多次调用间共享。应使用 None 作为哨兵，在函数体内新建对象。

可变位置参数收集位置参数，关键字参数收集具名参数，常用于装饰器和框架适配层。封装时要保留函数签名、类型提示和异常。

**Key words:** 可变默认参数、求值时机、哨兵、位置参数、关键字参数、装饰器

### Q08：迭代器、生成器、装饰器和上下文管理器分别解决什么问题？

**答案：**

- 迭代器实现逐个取值的协议；
- 生成器用 yield 保存执行状态，适合大数据和流式输出；
- 装饰器用高阶函数增加日志、鉴权、重试或缓存；
- 上下文管理器把资源进入和退出绑定起来，保证文件、锁、事务等在异常路径也能清理。

**Key words:** 迭代器、生成器、yield、装饰器、高阶函数、上下文管理器、资源生命周期

### Q09：Python 线程、进程、协程和 asyncio 怎么选？

**答案：**

I/O 密集且已有同步库可选线程；CPU 密集优先多进程或原生扩展；大量网络 I/O 适合协程和 asyncio。协程不是自动并行，一个协程执行同步阻塞代码会卡住整个事件循环，应把阻塞调用放进线程池。

**Key words:** 线程、进程、协程、asyncio、事件循环、I/O 密集、CPU 密集、线程池

### Q10：GIL 是什么？为什么 I/O 场景线程仍然有用？

**答案：**

GIL 是 CPython 的全局解释器锁，通常限制同一进程同一时刻只有一个线程执行 Python 字节码，因此不能靠 Python 多线程线性加速纯 CPU 代码。

线程等待网络、文件、数据库或释放 GIL 的 C 扩展时，其他线程仍可运行，所以 I/O 密集场景仍能提高吞吐。

**Key words:** GIL、CPython、字节码、I/O、CPU、多进程、C 扩展、吞吐

### Q11：FastAPI 里同步函数和异步函数怎么选？

**答案：**

调用链是异步 I/O 时使用 async def 和异步客户端；同步阻塞库不能直接放在 async handler 中，否则会阻塞事件循环，应使用同步 worker 或线程池。CPU 重任务应交给任务队列或独立进程。

FastAPI 的价值在于类型校验、依赖注入和 OpenAPI，不代表所有函数写成 async 就会更快。

**Key words:** FastAPI、async def、事件循环、同步阻塞、依赖注入、OpenAPI、线程池

### Q12：Python 引用计数和 GC 如何协作？为什么仍会内存泄漏？

**答案：**

引用计数快速释放大多数对象，循环引用由 GC 补充处理。长期持有全局列表、缓存、任务回调、未关闭生成器或后台任务，即使没有循环引用，也会让对象持续可达。

排查应结合 RSS、tracemalloc、对象数量、缓存和请求生命周期，不能只看 GC 次数。

**Key words:** 引用计数、循环引用、垃圾回收、tracemalloc、RSS、缓存、后台任务

## 三、Go 语法与运行时

### Q13：Go 的 new 和 make 有什么区别？

**答案：**

new(T) 分配 T 的零值并返回 *T；make 只用于 slice、map、channel，初始化运行时结构并返回可直接使用的值。slice、map、channel 赋值时可能共享底层数据或运行时对象，仍需明确修改权限。

**Key words:** new、make、零值、slice、map、channel、指针、共享数据

### Q14：Go slice 的底层结构和扩容会带来什么坑？

**答案：**

slice 包含指针、len 和 cap。截取通常共享底层数组；append 在容量足够时原地写入，容量不足时分配新数组并复制。传 slice 给函数只复制 header，不会自动复制元素。

需要隔离修改时显式 copy，需要减少扩容时预估容量。返回 slice 时要说明调用方是否能修改底层数据。

**Key words:** slice header、len、cap、append、底层数组、共享、copy、扩容

### Q15：Go map 的无序遍历和并发安全怎么回答？

**答案：**

map 是哈希表，键必须可比较；遍历顺序不承诺稳定，业务不能依赖它。普通 map 不是并发安全的，并发读写可能 panic。

读多写少可用 RWMutex，特定访问模式才评估 sync.Map。删除、扩容和并发访问都应通过测试和 profile 验证，而不是凭直觉选容器。

**Key words:** map、哈希表、可比较 key、无序遍历、扩容、并发安全、RWMutex、sync.Map

### Q16：channel 的关闭规则和 goroutine 泄漏问题是什么？

**答案：**

通常由发送方关闭 channel；关闭后仍可读出缓冲数据，继续读取得到零值和 ok=false；向已关闭 channel 发送或重复关闭会 panic。

goroutine 可能因永远等待、无人接收、外部 I/O 没有超时或忘记取消而泄漏。要用 context、超时、明确的 owner 和退出路径管理生命周期。

**Key words:** channel、缓冲、关闭、ok、panic、goroutine 泄漏、context、超时

### Q17：Mutex、原子操作、Once、WaitGroup 和 sync.Map 如何分工？

**答案：**

原子操作适合独立计数和状态位；Mutex/RWMutex 保护多字段不变量；Once 保证初始化只执行一次；WaitGroup 只等待一组 goroutine，不能承担错误传播；sync.Map 只适合特定读多写少模式。

锁内不要做网络请求或不可控阻塞，重点是缩短临界区并保证所有退出路径解锁。

**Key words:** Mutex、RWMutex、原子操作、CAS、Once、WaitGroup、sync.Map、临界区

### Q18：context 在 Go 服务里解决什么问题？

**答案：**

context 传递取消信号、deadline 和少量请求范围元数据。HTTP、数据库、RPC 和后台 goroutine 应把 context 贯穿到底层调用；创建 cancel context 后要调用 cancel，避免定时器和子节点泄漏。

context 不是通用参数包，也不应该存放大对象。收到 Done 后必须真正停止工作或释放资源。

**Key words:** context、取消、deadline、timeout、Done、请求链路、元数据、资源泄漏

### Q19：GMP、逃逸分析和 Go GC 如何串起来？

**答案：**

G 是 goroutine，M 是内核线程，P 是执行 Go 代码所需的调度资源；P 维护本地队列，空闲时可窃取其他 P 的任务。阻塞调用、抢占、channel 操作和 GC 都可能触发调度。

逃逸分析决定对象放栈还是堆；闭包捕获、返回局部地址、放入 interface 等可能导致逃逸。Go 的并发标记清扫 GC 通过写屏障维护对象关系，但 goroutine、缓存、定时器和 channel 仍可能造成内存泄漏。

**Key words:** GMP、goroutine、work stealing、调度、逃逸分析、堆、栈、并发 GC、写屏障、pprof

## 四、并发与服务工程

### Q20：如何设计一个不会阻塞的异步接口？

**答案：**

入口快速校验并生成请求 ID，外部 I/O 使用异步客户端；CPU 密集和同步库放到线程池/进程池；长任务返回任务 ID，通过轮询、SSE 或 WebSocket 推送进度。

同时设置连接、读取和总超时，传递取消信号，限制并发数和队列长度，并在下游失败时释放资源。压测看 p95/p99、事件循环延迟、队列长度和错误率。

**Key words:** 异步接口、事件循环、线程池、任务队列、SSE、超时、取消、背压、p99

### Q21：语言层性能优化如何验证？

**答案：**

先建立基线，再用 profile/benchmark 找 CPU、内存、锁、I/O 或分配热点；修改后用相同数据、并发和环境复测，比较吞吐、延迟、峰值内存和错误率。

优先减少不必要复制、阻塞、序列化和上下文切换，最后才做语法微优化。单次 wall time 不能证明线上收益。

**Key words:** 基线、benchmark、profile、吞吐、延迟、p95、p99、内存、分配、序列化

### Q22：语言题如何体现工程能力？

**答案：**

不要停留在“语法是什么”，还要回答对象是否共享、谁负责释放、取消是否真正传到底层、错误能否重试、重试是否幂等、队列满时如何背压，以及如何通过日志、指标和 trace 验证。

语言只是实现层；服务质量取决于生命周期、资源上限、并发边界和可观测性。

**Key words:** 共享状态、生命周期、取消、泄漏、重试、幂等、资源上限、背压、可观测性
