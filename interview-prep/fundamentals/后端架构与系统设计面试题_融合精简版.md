## 一、架构基本功

### Q01：系统设计题应该先问什么？如何拆需求？

**答案：**

先确认用户、核心流程、读写比例、数据规模、峰值并发、延迟目标、可用性、合规和成本，再明确哪些是本期范围、哪些可以异步或最终一致。

把需求拆成：入口/API、核心领域逻辑、数据存储、缓存、消息、外部依赖、运维与安全。先画数据流和故障边界，再选择组件，避免一上来就堆技术名词。

**Key words:** 功能需求、非功能需求、QPS、p95、可用性、数据规模、故障边界、成本

### Q02：单体、模块化单体和微服务怎么选？

**答案：**

单体部署简单、事务和调试成本低，适合早期或边界不稳定的系统；模块化单体在一个进程内保持清晰领域边界，是常见的渐进式选择；微服务适合团队、发布节奏和扩展需求已经形成差异的场景。

微服务带来网络调用、数据一致性、部署、观测和治理成本。拆分应基于领域边界、独立扩展和故障隔离，而不是按数据库表或组织架构机械切分。

**Key words:** 单体、模块化单体、微服务、领域边界、独立部署、故障隔离、治理成本

### Q03：什么是无状态服务？状态应该放在哪里？

**答案：**

无状态服务不把用户会话和任务状态只放在某个实例内，请求可被任意实例处理，便于水平扩展和故障转移。状态可放在数据库、Redis、对象存储或可靠消息系统中，并设计过期、版本和恢复策略。

本地缓存和临时连接仍可存在，但不能成为唯一真相；如果必须粘性会话，要说明路由、故障转移和扩容代价。

**Key words:** 无状态、水平扩展、会话、Redis、数据库、对象存储、粘性会话、故障转移

### Q04：CAP、BASE 和一致性模型怎么用于实际设计？

**答案：**

网络分区发生时，分布式系统不能同时保证完美一致性和始终可用；CAP 不是三选一的日常标签，而是帮助说明分区场景的取舍。BASE 允许基本可用、软状态和最终一致，以换取可用性和扩展性。

设计时要按数据类型区分：余额、库存和权限通常需要强约束；推荐、计数和搜索索引可接受短暂不一致。明确读写路径、版本、冲突处理和用户可见的暂态状态。

**Key words:** CAP、网络分区、BASE、强一致、最终一致、冲突、版本、可用性

### Q05：水平扩展为什么需要负载均衡和服务发现？

**答案：**

水平扩展是增加实例而不是只升级单机。负载均衡按轮询、权重、最少连接或一致性哈希分发请求；服务发现维护实例地址、健康状态和版本，配合连接池与优雅下线。

还要考虑连接复用、会话状态、区域/故障域、健康检查误判和扩容时的缓存预热。

**Key words:** 水平扩展、负载均衡、服务发现、健康检查、连接池、一致性哈希、优雅下线

### Q06：API 设计要考虑哪些工程问题？

**答案：**

接口要明确资源语义、输入校验、错误码、超时、分页、排序、版本兼容和幂等性。写请求应带请求 ID 或幂等键，返回可重试信息；长任务使用任务 ID 与状态查询或事件流。

对外 API 需要认证、授权、限流和审计；内部 RPC 需要超时、重试、熔断和 schema 兼容。接口契约先于实现，避免客户端依赖数据库字段。

**Key words:** API、版本、幂等键、分页、错误码、请求 ID、超时、重试、认证、授权

## 二、数据与高并发

### Q07：缓存、数据库和消息队列在架构中分别做什么？

**答案：**

数据库保存可追溯的事实数据；缓存减少热点读延迟和数据库压力；消息队列承担异步解耦、削峰填谷和事件传播。三者的可靠性和一致性边界不同，不能把缓存或队列当作数据库的无条件替代。

要定义写入真相、缓存失效、消息确认、重复消费和补偿策略，才能回答“数据会不会丢、会不会旧、失败怎么恢复”。

**Key words:** 数据库、缓存、消息队列、事实数据、削峰、解耦、失效、补偿

### Q08：高并发请求如何从入口流到下游？

**答案：**

典型链路是 CDN/网关限流 → 负载均衡 → 无状态应用 → 本地/分布式缓存 → 数据库或消息队列。入口要尽早拒绝无效请求，应用要限制并发和队列长度，下游要设置连接池与超时。

当下游变慢时，背压、降级和舱壁隔离比无限重试更重要；异步化只能转移压力，不能消灭总工作量。

**Key words:** 网关、限流、负载均衡、缓存、连接池、队列、背压、降级、舱壁隔离

### Q09：幂等、去重和分布式锁分别解决什么问题？

**答案：**

幂等保证同一业务请求重复执行结果可控；去重记录已经处理的请求/事件；分布式锁协调同一资源的并发访问。优先使用数据库唯一约束、条件更新或单线程分区，只有跨实例协调且确有竞争时才使用分布式锁。

锁要有 token、过期、续租、释放校验和失败兜底；无论有没有锁，支付、下单和消息消费都应设计幂等。

**Key words:** 幂等、去重、唯一约束、条件更新、分布式锁、token、续租、消息消费

### Q10：消息队列的至少一次、至多一次和恰好一次怎么理解？

**答案：**

- 至多一次：先确认再处理，可能丢消息但不重复；
- 至少一次：处理成功后确认，可能因重试重复；
- 恰好一次通常只在受控事务边界内成立，跨数据库和消息系统很难端到端保证。

工程上通常选择至少一次，再用业务幂等键、去重表、事务外盒、重试退避和死信队列处理重复与失败。

**Key words:** 至多一次、至少一次、恰好一次、ACK、幂等、事务外盒、重试、死信队列

### Q11：限流、熔断、降级、重试和超时如何配合？

**答案：**

限流控制入口速率，熔断在下游连续失败时快速失败，降级返回缓存/默认结果或关闭非核心功能，超时释放等待资源，重试只适用于临时错误且必须带退避和次数上限。

每层都设超时会形成总延迟预算；重试次数相乘可能造成流量放大。要传递取消信号，并为关键依赖设置舱壁隔离。

**Key words:** 限流、熔断、降级、超时、重试、指数退避、延迟预算、舱壁隔离

### Q12：读写分离、分库分表和分片键如何设计？

**答案：**

读写分离用副本承载查询，但要接受复制延迟，关键读可走主库或等待位点。分库分表首先选择稳定、均匀且常用于查询的分片键，再处理全局 ID、跨分片查询、事务、扩容和热点。

分片不是性能万能药；单表索引、SQL、缓存、归档和批处理优化应先做。

**Key words:** 读写分离、复制延迟、分片键、全局 ID、跨分片查询、扩容、热点

### Q13：如何设计可靠的任务/事件处理系统？

**答案：**

入口写入任务记录和幂等键，再投递消息；消费者领取任务、更新状态、执行外部调用并保存结果。状态机要区分待处理、处理中、成功、可重试失败和终态失败，避免重复执行造成副作用。

重试要指数退避并设置上限，超过上限进入死信或人工处理；定时扫描和补偿任务负责修复“写库成功但发消息失败”等半成功状态。

**Key words:** 任务状态机、幂等键、消费者、重试、死信、补偿、半成功、外部副作用

## 三、可靠性与工程治理

### Q14：SLO、SLI、SLA 和错误预算有什么关系？

**答案：**

SLI 是测量指标，如成功率、延迟和新鲜度；SLO 是内部目标；SLA 是对客户的承诺。错误预算是允许的失败额度，用于平衡发布速度与稳定性。

设计 SLO 要按用户旅程定义，区分平均值与 p95/p99，并把依赖、异步任务和数据正确性纳入，而不只看 HTTP 200。

**Key words:** SLI、SLO、SLA、错误预算、成功率、p95、p99、数据正确性

### Q15：日志、指标、Trace 如何形成可观测性？

**答案：**

指标回答“是否变坏”，日志回答“发生了什么”，Trace 回答“一次请求经过哪些组件、在哪一步变慢”。统一 request ID/trace ID，结构化记录状态、耗时、重试和错误原因。

高并发系统要控制采样和敏感数据，避免日志本身成为瓶颈；告警应指向用户影响和可执行动作。

**Key words:** 日志、指标、Trace、request ID、trace ID、结构化日志、采样、告警

### Q16：重试风暴、雪崩和级联故障如何避免？

**答案：**

为每个调用设置总超时和重试预算，使用指数退避、随机抖动、熔断、舱壁和限流；缓存失效要打散，任务队列要有界，依赖恢复时要逐步放量。

排障时看调用图、队列长度、连接池、线程池、CPU 和错误率，区分根因故障与放大器，不能只给所有服务“加机器”。

**Key words:** 重试风暴、级联故障、指数退避、抖动、熔断、舱壁、队列、有界资源

### Q17：RPO、RTO、备份和容灾怎么回答？

**答案：**

RPO 表示最多能丢多少数据，RTO 表示最多多久恢复服务。备份要有全量/增量、异地副本、加密、保留周期和恢复演练；高可用不等于备份，主从同步也不等于防误删。

按故障域设计单机、机架、可用区和地域级恢复方案，并根据业务重要性决定成本。

**Key words:** RPO、RTO、备份、恢复演练、异地副本、故障域、可用区、误删

### Q18：滚动、蓝绿和金丝雀发布如何选择？

**答案：**

滚动发布逐步替换实例，资源成本低但新旧版本共存；蓝绿发布保留两套环境，切换和回滚快但成本高；金丝雀按小流量、用户或区域验证，适合高风险变更。

数据库迁移要向前兼容，先加字段再切流，避免回滚代码时 schema 不兼容。发布必须有健康检查、指标门禁和自动回滚。

**Key words:** 滚动发布、蓝绿、金丝雀、灰度、向前兼容、数据库迁移、自动回滚

### Q19：安全架构里最重要的边界是什么？

**答案：**

按最小权限和零信任思路保护身份、网络、数据和工具：认证确认是谁，授权确认能做什么，审计记录做过什么。敏感数据加密传输和存储，密钥轮换，输入校验，依赖和镜像扫描。

内部服务也不能默认可信；尤其是可执行代码、文件、SQL、命令和模型生成参数，必须经过白名单、沙箱和资源限制。

**Key words:** 最小权限、零信任、认证、授权、审计、加密、密钥轮换、沙箱、白名单

## 四、Agent 系统设计

### Q20：Agentic Workflow 和普通 Workflow 有什么区别？

**答案：**

普通 Workflow 的步骤和分支基本固定，便于预测和测试；Agentic Workflow 让模型根据上下文选择工具、路径或下一步，但需要状态机、预算、护栏和人工接管保证边界。

生产系统应把确定性步骤写死，把需要判断的局部交给模型，并对每一步记录输入、工具、结果和退出条件。

**Key words:** Workflow、Agentic Workflow、状态机、工具选择、预算、Guardrail、人工接管

### Q21：一个 RAG 服务的架构和瓶颈在哪里？

**答案：**

离线链路负责文档解析、切分、元数据、向量化和索引；在线链路负责鉴权、查询改写、召回、过滤、重排、上下文拼装和模型生成。缓存可放查询、embedding 和热门文档，异步队列负责索引更新。

优化要区分召回率、重排质量、上下文长度、首 token 延迟、模型成本和数据新鲜度，并用离线集、线上 trace 和回归集验证。

**Key words:** RAG、切分、embedding、向量检索、召回、重排、上下文、数据新鲜度、Eval

### Q22：Agent 工具调用如何做安全和可靠性设计？

**答案：**

工具定义要有 schema、权限、超时、速率和副作用说明；执行前做参数校验和授权，危险操作需要人工确认或沙箱。执行后记录结果、耗时、trace 和可重试性。

外部副作用工具要使用幂等键、幂等接口和补偿；模型输出只能作为不可信输入，不能直接拼接 SQL、Shell 或文件路径。

**Key words:** Tool Calling、schema、权限、超时、沙箱、人工确认、幂等键、不可信输入

### Q23：Agent 的短期记忆、长期记忆和共享状态怎么分层？

**答案：**

短期记忆服务当前任务上下文，随任务结束或压缩；长期记忆保存经过筛选的用户偏好、事实和历史摘要；共享状态记录工作流进度、工具结果和多 Agent 协作状态。

每类状态都要有作用域、版本、过期、隐私和删除策略，不能把完整对话无限塞进 prompt 或 Redis。

**Key words:** 短期记忆、长期记忆、共享状态、作用域、摘要、版本、过期、隐私

### Q24：Multi-Agent 如何避免成本和复杂度失控？

**答案：**

先定义角色、输入输出契约和停止条件，再选择 planner/executor/verifier 或 supervisor/worker 等模式。限制并发 Agent 数、token、工具调用次数和总耗时，失败时能回退到单 Agent 或人工流程。

Agent 之间传递结构化任务和结果，不要无边界共享完整上下文；用 trace 评估路由正确率、任务完成率、成本和重复劳动。

**Key words:** Multi-Agent、planner、executor、verifier、supervisor、停止条件、token 预算、trace

### Q25：Agent 系统如何做 Eval 和线上回归？

**答案：**

同时评估最终结果和执行轨迹：任务成功率、工具选择、参数正确性、步骤数、延迟、成本、安全拦截和人工接管率。数据要拆成开发集、保留集和回归集，规则检查与模型评审结合。

每次改 prompt、工具、路由或模型都记录版本并重放代表性 trace；发现 badcase 后补测试和护栏，而不是只调一个总分。

**Key words:** Eval、Trace、badcase、回归集、任务成功率、工具正确性、成本、人工接管

### Q26：系统设计题最后如何收束？

**答案：**

用一张图说明请求链路、数据真相、异步边界、故障隔离和观测点；再给出容量假设、关键取舍、降级方案、扩容路径和最先落地的 MVP。

回答要主动说清“什么不做”和“哪里最终一致”，并用指标验证设计是否达到延迟、可用性、成本和正确性目标。

**Key words:** 请求链路、数据真相、异步边界、故障隔离、容量假设、MVP、降级、扩容

## 速刷顺序

优先掌握：需求拆解、无状态与扩展、CAP/一致性、缓存/数据库/消息、幂等与重试、可观测性、发布回滚，以及 Agent 的工具安全和 Eval 闭环。
