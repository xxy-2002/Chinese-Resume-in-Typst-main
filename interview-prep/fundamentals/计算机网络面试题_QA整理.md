## 1. 网络模型

### 1.1 OSI七层模型和TCP/IP模型分别介绍一下？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**OSI七层模型：**

开放式系统互联通信参考模型（Open System Interconnection Reference Model），主要有7层：

| 层级 | 名称 | 主要职能 |
|------|------|---------|
| 第7层 | 应用层 | 负责给应用程序提供统一的接口 |
| 第6层 | 表示层 | 负责把数据转换成兼容另一个系统能识别的格式 |
| 第5层 | 会话层 | 负责建立、管理和终止表示层实体之间的通信会话 |
| 第4层 | 传输层 | 负责端到端的数据传输 |
| 第3层 | 网络层 | 负责数据的路由、转发、分片 |
| 第2层 | 数据链路层 | 负责数据的封帧和差错检测，以及MAC寻址 |
| 第1层 | 物理层 | 负责在物理网络中传输数据帧 |

**TCP/IP模型：**

TCP/IP协议被组织成4个概念层：

| 层级 | 名称 | 说明 |
|------|------|------|
| 第4层 | 应用层 | 支持HTTP、SMTP等最终用户进程 |
| 第3层 | 传输层 | 处理主机到主机的通信（TCP、UDP） |
| 第2层 | 网络层 | 寻址和路由数据包（IP协议） |
| 第1层 | 网络接口层 | 通过网络的物理电线、电缆或无线信道移动比特 |

**关键点：** OSI模型复杂且是理论模型，TCP/IP模型是实际使用的模型。

## 2. HTTP协议

### 2.1 HTTP报文有哪些部分？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**HTTP请求报文：**

```
┌─────────────────────────────────────┐
│  1. 请求行（Request Line）          │  ← 方法 + URL + HTTP版本
├─────────────────────────────────────┤
│  2. 请求头部（Request Headers）     │  ← Host, User-Agent, Content-Type等
├─────────────────────────────────────┤
│  3. 空行                            │  ← 请求头和请求体分隔
├─────────────────────────────────────┤
│  4. 请求体（Request Body）          │  ← 可选，POST/PUT数据
└─────────────────────────────────────┘
```

**HTTP响应报文：**

```
┌─────────────────────────────────────┐
│  1. 状态行（Status Line）           │  ← HTTP版本 + 状态码 + 状态信息
├─────────────────────────────────────┤
│  2. 响应头部（Response Headers）    │  ← Content-Type, Content-Length等
├─────────────────────────────────────┤
│  3. 空行                            │  ← 响应头和响应体分隔
├─────────────────────────────────────┤
│  4. 响应体（Response Body）         │  ← HTML, JSON等内容
└─────────────────────────────────────┘
```

### 2.3 HTTP返回状态301和302分别是什么？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

| 状态码 | 名称 | 含义 |
|--------|------|------|
| 301 | Moved Permanently | **永久重定向**：请求的资源已经不存在，需改用新的URL再次访问 |
| 302 | Found | **临时重定向**：请求的资源还在，但暂时需要用另一个URL来访问 |

**实际应用：**
- 301：用于域名更换、HTTP迁移到HTTPS等永久性变更
- 302：用于临时性维护、页面A/B测试等临时性变更

### 2.4 HTTP 502和504的区别是什么？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

| 状态码 | 名称 | 含义 | 示例 |
|--------|------|------|------|
| 502 | Bad Gateway | 网关收到无效响应 | nginx收到后端服务器返回的无效响应 |
| 504 | Gateway Timeout | 网关超时未收到响应 | nginx等待后端服务器超时 |

**举例说明：**
- nginx作为代理服务器，收到客户端请求后转发到后端服务器（Tomcat等）
- 502：后端服务器返回了无效响应（如500错误被nginx认为无效）
- 504：超过nginx配置的超时时间，后端服务器未响应

### 2.6 GET和POST的使用场景，有哪些区别？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**GET方法特点：**
- 语义：从服务器获取指定资源
- 参数位置：URL中（?key=value&...）
- 长度限制：浏览器对URL长度有限制
- 数据类型：只支持ASCII字符
- 缓存：可被缓存，可保存为书签

**POST方法特点：**
- 语义：根据请求负荷对指定资源做出处理
- 参数位置：请求体中
- 长度限制：浏览器无限制
- 数据类型：任意格式（需协商）
- 缓存：一般不被缓存

**RFC规范语义：**
- GET是安全且幂等的（只读操作）
- POST是非安全非幂等的（会修改数据）

**注意：** 实际开发中可能不按RFC规范实现。

### 2.7 HTTP的长连接是什么？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**HTTP短连接：**
```
建立TCP → 请求 → 响应 → 释放TCP → 建立TCP → 请求 → 响应 → 释放TCP...
```
每次请求都要建立和释放TCP连接，效率低。

**HTTP长连接（Keep-Alive）：**
```
建立TCP → 请求 → 响应 → 请求 → 响应 → ... → 释放TCP
```
使用同一个TCP连接发送多个HTTP请求/响应，避免连接建立和释放的开销。

**特点：** 任意一端没有明确提出断开连接，则保持TCP连接状态。

**默认端口：** HTTP是80，HTTPS是443。

### 2.8 HTTP1.1怎么对请求做拆包？

**掌握程度：⭐⭐⭐（6星）**
**考察频次：⭐⭐⭐（5星）**

**答案：**

通过`Content-Length`头字段来指示请求正文的长度。

**工作流程：**
1. 客户端发送请求时，在请求头中添加`Content-Length`字段
2. 该字段的值表示请求正文的字节数
3. 服务器根据`Content-Length`字段的值确定请求长度
4. 从请求中读取相应数量的字节，直到读取完整个请求内容

**作用：** 确保服务器正确接收到完整的请求，避免请求丢失或截断。

### 2.9 HTTP断点重传是什么？

**掌握程度：⭐⭐⭐（6星）**
**考察频次：⭐⭐（4星）**

**答案：**

HTTP/1.1协议支持的特性，实现大文件下载的断点续传。

**流程：**
1. 客户端开始下载文件，服务端发送`Accept-Ranges: bytes`声明支持断点续传
2. 客户端下载过程中断后，再次下载时在HTTP头中声明：`Range: bytes=512000-`
3. 服务端返回`206 Partial Content`，并发送对应片段
4. 客户端继续下载剩余部分

**关键HTTP头：**
- `Accept-Ranges: bytes`：服务端声明支持范围请求
- `Range: bytes=start-end`：客户端请求的片段范围
- `Content-Range: bytes start-end/total`：服务端返回的片段信息
- `Content-Length`：片段的长度

### 2.10 HTTP为什么不安全？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：**

HTTP是明文传输，存在三大安全风险：

| 风险 | 描述 | 后果 |
|------|------|------|
| 窃听风险 | 通信链路可被监听 | 用户账号被盗 |
| 篡改风险 | 强制植入垃圾广告 | 视觉污染，用户体验差 |
| 冒充风险 | 冒充正规网站 | 经济损失 |

**HTTPS解决方案：**
- 信息加密：交互信息无法被窃取
- 校验机制：无法篡改通信内容
- 身份证书：证明服务器的真实性

### 2.11 HTTP和HTTPS的区别？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**主要区别：**

| 方面 | HTTP | HTTPS |
|------|------|-------|
| 安全性 | 明文传输，不安全 | 加密传输，安全 |
| 端口 | 80 | 443 |
| 连接建立 | TCP三次握手后直接传输 | TCP三次握手后还需TLS握手 |
| 证书 | 不需要 | 需要CA数字证书 |
| 性能 | 相对较高 | 相对较低（有加密开销） |

### 2.12 HTTPS握手过程说一下？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**TLS四次握手流程：**

```
┌─────────────────────────────────────────────────────────────────┐
│  客户端                                                          │
├─────────────────────────────────────────────────────────────────┤
│  1. Client Hello                                                │
│     - 支持的TLS协议版本                                          │
│     - 随机数（Client Random）                                    │
│     - 支持的密码套件列表                                         │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  服务端                                                          │
├─────────────────────────────────────────────────────────────────┤
│  2. Server Hello                                                │
│     - 确认TLS协议版本                                            │
│     - 随机数（Server Random）                                    │
│     - 确认的密码套件列表                                         │
│     - 服务器数字证书                                             │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  客户端                                                          │
├─────────────────────────────────────────────────────────────────┤
│  3. Client Key Exchange                                         │
│     - 随机数（pre-master secret，用公钥加密）                    │
│     - 加密通信算法改变通知                                       │
│     - 握手结束通知                                               │
│                                                                 │
│     客户端计算会话密钥                                           │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  服务端                                                          │
├─────────────────────────────────────────────────────────────────┤
│  4. Server Hello Done + Encrypted Handshake Message             │
│     - 加密通信算法改变通知                                       │
│     - 握手结束通知                                               │
│                                                                 │
│     服务端计算会话密钥                                           │
└─────────────────────────────────────────────────────────────────┘
```

**三个随机数：** Client Random + Server Random + pre-master secret → 会话密钥

### 2.13 HTTPS是如何防范中间人攻击的？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**防范机制：**

1. **加密：** 通过非对称加密协商对称密钥
2. **身份校验：** 服务器数字证书验证

**具体流程：**
1. 服务器向CA申请数字证书，证书包含服务器公钥
2. 客户端验证证书的合法性（有效期、颁发机构信任链）
3. 客户端使用证书中的公钥加密通信数据
4. 服务器用私钥解密数据

**为什么能防范中间人：**
- 攻击者无法获得服务器的私钥
- 无法正确解密客户端发送的加密数据
- 证书验证失败会发出警告或中止连接

### 2.14 HTTP1.1和HTTP2.0的区别是什么？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：**

| 特性 | HTTP/1.1 | HTTP/2.0 |
|------|----------|----------|
| **头部压缩** | 不支持 | 支持（HPACK算法） |
| **报文格式** | 纯文本 | 二进制格式（帧） |
| **并发传输** | 队头阻塞 | 多路复用（Stream） |
| **服务器推送** | 不支持 | 支持 |
| **安全性** | 可选 | 基于HTTPS |

**关键改进：**
1. **头部压缩：** 消除重复头部，只发送索引号
2. **二进制帧：** 头信息帧和数据帧，提高解析效率
3. **多路复用：** 多个Stream复用一条TCP连接，解决队头阻塞
4. **服务器推送：** 服务端主动向客户端发送资源

### 2.15 HTTP进行TCP连接之后，在什么情况下会中断？

**掌握程度：⭐⭐⭐（6星）**
**考察频次：⭐⭐⭐（5星）**

**答案：**

| 情况 | 说明 |
|------|------|
| **close系统调用** | 发送FIN报文，进行四次挥手 |
| **超时重传失败** | 发送数据后，接收方超过时间未响应ACK，达到最大重传次数 |
| **连接超时** | HTTP长时间没有请求和响应，超过保活时间释放连接 |

### 2.16 HTTP、SOCKET和TCP的区别？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

| 概念 | 层级 | 说明 |
|------|------|------|
| **HTTP** | 应用层协议 | 定义客户端和服务器之间交换的数据格式和规则 |
| **Socket** | 编程接口 | 提供了网络通信的API，是通信的一端 |
| **TCP** | 传输层协议 | 负责在网络中建立可靠的数据传输连接 |

**关系：**
- HTTP基于TCP实现
- Socket是编程接口，可以基于TCP或UDP
- TCP是传输层的可靠连接协议

### 一、先点明核心差异（展示基本功）

> “SSE和WebSocket都是全双工通信的解决方案，但WebSocket是真正的双向持久连接，而SSE是基于HTTP/1.1或HTTP/2的单向推送（客户端发一次请求，服务器可持续多次响应）。”

| 维度 | SSE | WebSocket |
|------|-----|------------|
| 通信方向 | 单向（服务端→客户端） | 双向实时 |
| 协议 | HTTP（更友好，穿透性好） | 独立协议（ws/wss） |
| 自动重连 | 内置支持 | 需手动实现 |
| 二进制数据 | 需编码 | 原生支持 |
| 连接状态 | 轻量（无复杂握手） | 需要心跳保活 |

---

### 二、为什么Agent场景更适合SSE？（核心得分点）

Agent服务（如大模型对话、自动执行任务）的典型数据流是：
**用户发送一次指令 → Agent分步处理 → 服务端主动持续推送中间结果**。

这种情况下，**客户端几乎不需要额外发送数据**，SSE恰好完美匹配：

#### 1. **语义更清晰，实现更简单**
- SSE就是为“服务器推送流式数据”设计的，代码只需处理`data:`块；
- WebSocket需要管理消息类型（发/收）、心跳、断线重连逻辑，增加了不必要的复杂度。

#### 2. **更好的基础设施兼容性**
- SSE基于标准HTTP，可以直接复用现有的**负载均衡器、CDN、代理、防火墙**（WebSocket需要单独配置升级协议和超时）。
- 很多企业内网会拦截非HTTP流量，SSE不存在这个问题。

#### 3. **资源占用更少**
- WebSocket为了维持双向实时，需要周期心跳（即使无数据），长期闲置连接会产生内存和CPU开销；
- SSE是“长轮询的优雅版本”，只在有数据推送时才活跃，空闲时只占用一个HTTP连接槽。

#### 4. **自动重连天然支持**
- SSE规范自带`Last-Event-ID`和自动重连机制，断电断网后可以恢复未接收的消息；
- WebSocket断开后需要自己实现指数退避重连 + 消息去重/补发逻辑。

#### 5. **符合Agent的实际交互模式**
> “Agent的典型流程是：`ask → think → tool_call → think → answer`，这个过程中客户端只在第一步需要发送数据（选哪个工具、用户确认等），后续全部是服务端主动推送状态和结果。如果使用WebSocket，反而要额外处理客户端不必要的上行通道，增加了协议设计的复杂度。”

---

### 三、什么时候应该用WebSocket？（展示辩证思维）

面试官可能会追问：“那WebSocket就完全没用了？”——你需要主动补充：

> “如果Agent需要**频繁的双向交互**，比如：
> - 用户在Agent执行过程中，可以**随时打断、修改参数、插入新指令**；
> - Agent需要**同时推送音视频流**（二进制数据）；
> - 或者需要**服务端主动向客户端请求信息**（例如验证码、外部授权回调）；
>
> 这种情况下，WebSocket的双向实时性就更有优势。但目前主流对话式Agent（如ChatGPT、Claude）都采用了SSE，因为用户主动打断的场景可以通过发送新的HTTP请求取消旧流来实现，不需要维持全双工通道。”

---

### 四、面试中的加分补充（技术深度）

如果你想更进一步，可以提一下**HTTP/2 + SSE的组合优势**：

> “在HTTP/2环境下，SSE可以复用一个TCP连接推送多个不同数据流（通过不同的流ID），既避免了WebSocket的协议切换开销，又能实现一定程度的“伪多路复用”。同时，配合`Transfer-Encoding: chunked`或`x-accel-buffering: no`，可以做到真正的流式推送，和WebSocket在延迟上没有显著差异。”

---

### 五、一个极简的总结金句（方便面试最后概括）

> **“SSE是‘上半场’的完美协议——当你的数据流是客户端发一次、服务端持续推多次时，用SSE能得到更简单的代码、更好的兼容性和更低的资源开销。WebSocket是为‘全场对攻’准备的，如果你的Agent需要像真人对话那样你一句我一句频繁交互，那才值得使用WebSocket。”**

## 4. DNS域名解析

### 4.1 DNS的全称了解么？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**DNS：** Domain Name System（域名系统）

**作用：** 互联网中用于将域名转换为对应IP地址的分布式数据库系统

**域名层级：**
```
根域(.) → 顶级域(.com) → 权威域(server.com) → 子域(www.server.com)
```

**层级特点：**
- 越靠右的位置表示层级越高
- 根域DNS服务器信息保存在所有DNS服务器中
- 任何DNS服务器都可以找到根域DNS服务器

```
┌─────────────────────────────────────────────────────────────────┐
│  1. 客户端发送DNS请求                                            │
│     问：www.server.com 的IP是什么？                             │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  2. 本地DNS服务器                                                │
│     - 查缓存：有则返回                                          │
│     - 无则问根DNS服务器                                          │

                              ↓
┌─────────────────────────────────────────────────────────────────┐

                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  4. 顶级域名服务器                                               │
│     回复：www.server.com归权威DNS服务器管                       │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  5. 权威DNS服务器                                                │
│     回复：对应的IP地址是 X.X.X.X                                │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  6. 本地DNS服务器缓存并返回给客户端                              │
└─────────────────────────────────────────────────────────────────┘
```

## 5. Cookie与Session

### 5.1 HTTP到底是不是无状态的？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：** HTTP是**无状态**的

**含义：** 每个请求都是独立的，服务器不会在多个请求之间保留关于客户端状态的信息

**状态保持的实现：**
- **Cookie：** 客户端存储状态信息
- **Session：** 服务器端存储状态信息

**为什么设计为无状态：**
- 使Web系统更具有规模化
- 简化服务器设计
- 提高缓存效率

---

### 5.2 携带Cookie的HTTP请求是有状态还是无状态的？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**HTTP协议本身仍是无状态的**，但通过Cookie实现了**状态保持**。

**解释：**
- HTTP协议设计保持无状态特性
- Cookie是无状态协议下的补充机制
- Cookie在客户端存储状态信息，服务器读取Cookie识别用户

**总结：** 使用Cookie可以实现状态保持，但HTTP协议本身仍是无状态的。

---

### 5.3 Cookie和Session有什么区别？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**对比表：**

| 方面 | Cookie | Session |
|------|--------|---------|
| **存储位置** | 客户端（浏览器） | 服务器端 |
| **数据容量** | 单个约4KB，有数量限制 | 理论上无限制（受服务器内存限制） |
| **安全性** | 较低（存储在客户端） | 较高（存储在服务器端） |
| **生命周期** | 可设置过期时间 | 浏览器关闭或超时失效 |
| **性能** | 每次请求发送到服务器 | 需要查询服务器 |
| **数据类型** | 字符串 | 任意类型 |

**工作原理：**
- Session ID通过Cookie传递给客户端
- 服务器通过Session ID查找对应的Session数据

---

### 5.4 Token、Session、Cookie的区别？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**对比表：**

| 方面 | Cookie | Session | Token |
|------|--------|---------|-------|
| **存储位置** | 客户端 | 服务器端 | 客户端 |
| **状态管理** | 需配合Session | 服务器管理状态 | 无状态 |
| **依赖** | 浏览器自动携带 | 依赖Cookie传递ID | 需手动添加 |
| **安全性** | 较低 | 较高 | 较高（签名） |
| **跨域支持** | 有限制 | 有限制 | 良好 |

**Token特点：**
- 无状态，用户信息加密到Token中
- 服务器收到Token后解密即可识别用户
- 适用于分布式系统和跨域场景

   ```

   ```
   - 缺点：URL不整洁，可能泄露Session ID

2. **隐藏表单字段**
   ```html
   <input type="hidden" name="sessionid" value="XXXXXX">
   ```
   - 缺点：仅适用于表单提交场景

**掌握程度：⭐⭐⭐⭐（8星）**

## 6. RPC与WebSocket

### 6.1 JWT令牌和传统方式有什么区别？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

| 方面 | 传统方式（Session/Cookie） | JWT令牌 |
|------|---------------------------|---------|
| **状态管理** | 有状态（服务器存储） | 无状态 |
| **存储位置** | 服务器端 | 客户端（令牌中包含所有信息） |
| **扩展性** | 集群需共享Session | 良好（每个服务器可独立验证） |
| **跨域支持** | 有限 | 良好 |
| **安全性** | 较高 | 较高（签名机制） |
| **性能** | 需查询Session | 无需查询（自包含） |

**JWT优势：**
- 无状态，分布式系统友好
- 自包含，服务器无需存储
- 跨域访问方便

---

### 6.2 JWT令牌都有哪些字段？

**掌握程度：⭐⭐⭐（6星）**
**考察频次：⭐⭐⭐（5星）**

**答案：**

JWT由三部分组成：

```
Header.Payload.Signature
```

**1. Header（头部）：**
```json
{
  "alg": "HS256",  // 签名算法
  "typ": "JWT"     // 令牌类型
}
```

**2. Payload（载荷）：**
```json
{
  "sub": "1234567890",  // 用户ID
  "name": "John Doe",   // 用户名
  "iat": 1516239022     // 签发时间
}
```

**3. Signature（签名）：**
```
HMAC-SHA256(
  base64UrlEncode(Header) + "." + base64UrlEncode(Payload),
  secret_key
)
```

---

### 6.3 JWT令牌为什么能解决集群部署问题？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**传统Session的问题：**
- 集群中每台服务器需要共享Session数据
- 需要引入Redis等共享存储
- 增加复杂性和性能开销

**JWT的解决方案：**
- 令牌中包含所有必要的身份验证信息
- 服务器无需存储会话信息
- 每个服务器可独立验证令牌

**优势：**
- 分布式系统中扩展方便
- 无需共享存储
- 提高系统可伸缩性和容错性

---

### 6.4 JWT的缺点是什么？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**主要缺点：** JWT一旦派发出去，在失效前都有效，**无法即时撤销**

**解决方案：**
- 业务层增加黑名单机制
- 使用内存数据库（如Redis）维护黑名单
- 每次验证JWT时检查是否在黑名单中

**其他缺点：**
- 令牌体积较大（包含完整信息）
- 无法修改已签发的令牌内容

---

### 6.5 JWT令牌如果泄露了，怎么解决？

**掌握程度：⭐⭐⭐（6星）**
**考察频次：⭐⭐⭐（5星）**

**答案：**

**解决方案：**

1. **及时失效令牌**
   - 将令牌标记为失效状态
   - 服务器拒绝处理失效令牌

2. **刷新令牌**
   - 检测到泄露后主动刷新
   - 生成新令牌，标记旧令牌失效

3. **黑名单机制**
   - 使用Redis维护黑名单
   - 每次请求检查令牌是否在黑名单

4. **缩短令牌有效期**
   - 设置较短的过期时间
   - 使用刷新令牌机制

### 6.6 前端是如何存储JWT的？

**掌握程度：⭐⭐⭐（6星）**
**考察频次：⭐⭐⭐（5星）**

**答案：**

| 存储方式 | 优点 | 缺点 |
|----------|------|------|
| **LocalStorage** | 存储空间大（5MB），不随请求发送 | 存在XSS攻击风险 |
| **SessionStorage** | 窗口关闭后自动清除，较安全 | 用户体验可能受影响 |
| **Cookie** | 可设置HttpOnly防止XSS | 大小限制（4KB），可能受CSRF攻击 |

**推荐：**
- 敏感度高的场景：Cookie + HttpOnly
- 需要跨标签页共享：LocalStorage
- 安全性优先：SessionStorage

### 6.7 为什么有HTTP协议了？还要用RPC？

**掌握程度：⭐⭐⭐（6星）**
**考察频次：⭐⭐⭐（5星）**

**答案：**

**RPC的本质：**
- RPC不是协议，而是一种调用方式
- 让程序员像调用本地方法那样调用远端服务方法
- gRPC和Thrift是具体的协议实现

**HTTP与RPC的区别：**

| 方面 | HTTP | RPC |
|------|------|-----|
| **设计目标** | B/S架构（浏览器-服务器） | C/S架构（客户端-服务器） |
| **性能** | HTTP/1.1较低，HTTP/2较高 | 通常性能更好 |
| **灵活性** | 标准协议，通用性强 | 可自定义，更灵活 |
| **使用场景** | 对外API | 内部服务通信 |

**实际应用：**
- 对外接口：使用HTTP协议
- 内部微服务：使用RPC协议

## 7. Nginx负载均衡

### 7.1 Nginx有哪些负载均衡算法？

**掌握程度：⭐⭐⭐⭐（8星）**

**答案：**

| 算法 | 说明 | 适用场景 |
|------|------|---------|
| **轮询（Round Robin）** | 按顺序依次分配请求 | 服务器性能相近 |
| **加权轮询** | 按权重分配请求 | 服务器性能不均 |
| **IP哈希** | 按客户端IP哈希分配 | 会话保持 |
| **URL哈希** | 按URL哈希分配 | 缓存优化 |
| **最少连接** | 分配给连接数最少的服务器 | 请求处理时间不均 |
| **最短响应时间** | 分配给响应时间最短的服务器 | 服务器性能不均 |

**Nginx默认使用轮询算法。**

## 8. TCP协议

### 8.1 说一下TCP的头部？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**TCP头部结构（20字节）：**

```
┌─────────────────────────────────────────────────────────────────┐
│  源端口(16)    │    目标端口(16)                                 │
├─────────────────────────────────────────────────────────────────┤
│  序列号(32)                                                      │
├─────────────────────────────────────────────────────────────────┤
│  确认应答号(32)                                                  │
├─────────────────────────────────────────────────────────────────┤
│  数据偏移(4) │ 保留(6) │ 标志位(6) │ 窗口大小(16)                │

│  校验和(16)   │    紧急指针(16)                                   │
├─────────────────────────────────────────────────────────────────┤
│  选项(可变长度)                                                  │
├─────────────────────────────────────────────────────────────────┤
```

**关键字段：**

| 字段 | 说明 |
|------|------|
| **序列号** | 标识发送的数据字节，解决乱序问题 |
| **确认应答号** | 期望收到的下一个序列号，解决丢包问题 |
| **ACK** | 确认应答有效 |
| **SYN** | 请求建立连接 |
| **FIN** | 请求断开连接 |
| **RST** | 强制断开连接 |
| **窗口大小** | 流量控制 |

### 8.2 TCP三次握手过程说一下？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**三次握手流程：**

```
客户端                              服务端
  │                                  │
  │    ────[SYN] seq=x─────────────> │  1. 客户端发送SYN（同步序列编号）
  │      (SYN-SENT)                  │     进入SYN-SENT状态
  │                                  │
  │    <───[SYN+ACK] seq=y,ack=x+1── │  2. 服务端发送SYN+ACK
  │      (SYN-RCVD)                  │     进入SYN-RCVD状态
  │                                  │
  │    ────[ACK] ack=y+1───────────> │  3. 客户端发送ACK
  │      (ESTABLISHED)               │     进入ESTABLISHED状态
  │                                  │
  │    <───[ESTABLISHED]──────────── │  4. 服务端进入ESTABLISHED状态
```

**关键点：**
- 第一次握手：SYN=1，不能携带数据
- 第二次握手：SYN=1，ACK=1，不能携带数据
- 第三次握手：ACK=1，**可以携带数据**
- 三次握手后，双方进入ESTABLISHED状态

---

### 8.3 TCP为什么需要三次握手建立连接？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：**

**三大原因：**

| 原因 | 说明 |
|------|------|
| **阻止历史连接** | 防止旧的重复连接初始化造成混乱 |
| **同步双方序列号** | 确保双方的初始序列号都能被确认 |
| **避免资源浪费** | 防止在网络拥堵时重复建立连接 |

**详细解释：**

1. **阻止历史连接（主要原因）**
   - 客户端发送SYN后宕机，重启后发送新的SYN
   - 三次握手可以通过序列号识别历史连接
   - 两次握手无法阻止，会建立无效连接

2. **同步双方序列号**
   - 序列号是可靠传输的关键因素
   - 双方都需要确认对方的初始序列号

3. **避免资源浪费**
   - 两次握手会导致服务器重复接收SYN
   - 造成半连接队列溢出

---

### 8.4 TCP三次握手，客户端第三次发送的确认包丢失了会发生什么？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**情况分析：**
- 客户端发送第三次ACK后进入ESTABLISHED状态
- 服务端收不到ACK，会触发**超时重传**
- 重传SYN-ACK报文，直到收到ACK或达到最大重传次数

**参数：**
- `tcp_synack_retries`：SYN-ACK最大重传次数（默认5次）

**过程：**
```
客户端                    服务端
  │                        │
  │────[SYN]─────────────> │
  │                        │
  │<───[SYN+ACK]────────── │
  │                        │
  │────[ACK]─────────────> │ ← 丢失
  │                        │
  │                        │ ← 超时重传SYN+ACK
  │<───[SYN+ACK]────────── │
  │                        │
  │────[ACK]─────────────> │ ← 重传成功
```

### 8.5 三次握手和accept是什么关系？accept做了哪些事情？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**关系：**
- TCP三次握手完成后，连接被保存到**内核的全连接队列**
- `accept()`函数从全连接队列中取出连接给应用程序使用

**accept的工作：**
1. 从内核的全连接队列取出已完成三次握手的连接
2. 返回新的文件描述符（socket）
3. 应用程序通过该描述符与客户端通信

**队列说明：**
- **半连接队列（SYN队列）：** 存储SYN_RECV状态的连接
- **全连接队列（Accept队列）：** 存储ESTABLISHED状态的连接，等待accept

---

### 8.6 客户端发送的第一个SYN报文，服务器没有收到怎么办？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**客户端行为：**
- 触发**超时重传**机制
- 重传SYN报文
- 序列号保持不变

**参数：**
- `tcp_syn_retries`：客户端SYN最大重传次数（默认5次）

**超时重传时间：**
- 第一次：1秒
- 第二次：2秒
- 第三次：4秒
- 第四次：8秒
- 第五次：16秒
- 第六次：32秒

**总耗时：** 约63秒（1+2+4+8+16+32）

---

### 8.7 服务器收到第一个SYN报文，回复的SYN+ACK报文丢失了怎么办？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**双方都会重传：**

| 角色 | 重传内容 | 参数 |
|------|---------|------|
| 客户端 | 重传SYN报文 | `tcp_syn_retries` |
| 服务端 | 重传SYN-ACK报文 | `tcp_synack_retries` |

**过程：**
1. 客户端收不到SYN-ACK，认为第一次握手丢失，重传SYN
2. 服务端收不到ACK，认为第二次握手丢失，重传SYN-ACK
3. 双方持续重传直到达到最大次数

---

### 8.8 第一次握手，客户端发送SYN报文后，服务端内部做了哪些工作？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**服务端内部流程：**
1. 收到SYN报文
2. 内核创建TCB（传输控制块）
3. 将连接存储到**半连接队列**
4. 向客户端发送SYN+ACK报文
5. 进入SYN_RCVD状态

**队列说明：**
- **半连接队列：** 存储未完成三次握手的连接
- **全连接队列：** 存储已完成三次握手等待accept的连接

**限制：** 两个队列都有最大长度限制，超限会丢弃或返回RST包。

---

### 8.9 大量SYN包发送给服务端会发生什么事情？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**SYN攻击（SYN Flood）：**
- TCP半连接队列被打满
- 后续SYN报文被丢弃
- 客户端无法建立连接

**解决方案：**

| 方法 | 说明 |
|------|------|
| **调大netdev max backlog** | 增加网卡队列长度 |
| **增大TCP半连接队列** | 调整三个参数 |
| **开启tcp_syncookies** | 绕开半连接队列 |
| **减少SYN+ACK重传次数** | 加快断开无效连接 |

**tcp_syncookies参数：**
- 0：关闭功能
- 1：半连接队列满时启用
- 2：始终启用

### 8.10 TCP四次挥手过程说一下？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**四次挥手流程：**

```
客户端                              服务端
  │                                  │
  │    ────[FIN]──────────────────> │  1. 客户端发送FIN（主动关闭）
  │      (FIN_WAIT_1)               │
  │                                  │
  │    <───[ACK]─────────────────── │  2. 服务端发送ACK
  │      (CLOSE_WAIT)               │
  │                                  │
  │                                │  3. 服务端处理完数据后发送FIN
  │    <───[FIN]────────────────── │
  │      (LAST_ACK)                 │
  │                                  │
  │    ────[ACK]──────────────────> │  4. 客户端发送ACK
  │      (TIME_WAIT)                │
  │                                  │
  │<───[TIME_WAIT结束]──────────── │  5. 客户端等待2MSL后关闭
  │      (CLOSED)                   │
```

### 8.11 为什么4次握手中间两次不能变成一次？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：**

**原因：**

| 步骤 | 说明 |
|------|------|
| **第二次挥手** | 服务端收到FIN后立即回复ACK，但可能还有数据要发送 |
| **第三次挥手** | 服务端处理完数据后才发送FIN |

**关键点：**
- 服务端收到FIN后，内核立即回ACK
- 但应用程序可能还有数据要发送
- 由应用程序决定何时发送FIN

**因此：** ACK和FIN一般分开发送，除非满足特定条件。

### 8.12 第二次和第三次挥手能合并吗？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：** **可以合并**，出现**三次挥手**

**条件：**
1. 被动关闭方**没有数据要发送**
2. **开启了TCP延迟确认机制**

**三次挥手示例：**
```
客户端                    服务端
  │                        │
  │────[FIN]─────────────> │
  │                        │
  │<───[FIN+ACK]────────── │ ← 合并发送
  │                        │
  │────[ACK]─────────────> │
```

### 8.13 第三次挥手一直没发，会发生什么？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**客户端状态：** FIN_WAIT2

**情况分析：**
- 如果用`shutdown`关闭（只关闭发送），可以持续保持FIN_WAIT2
- 如果用`close`关闭，会变成**孤儿连接**
- `tcp_fin_timeout`控制FIN_WAIT2的最大持续时间（默认60秒）
- 超时后连接直接关闭

**参数调整：**
```bash
echo 60 > /proc/sys/net/ipv4/tcp_fin_timeout
```

### 8.14 为什么四次挥手之后要等2MSL？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：**

**MSL：** Maximum Segment Lifetime，报文最大生存时间

**Linux设置：** MSL = 30秒

**2MSL的作用：**

1. **确保最后一个ACK能被接收**
   - 如果ACK丢失，服务端会重发FIN
   - 2MSL内可以收到重发的FIN并重传ACK

2. **确保网络中残留报文消失**
   - 防止旧连接的报文干扰新连接

**公式：** TIME_WAIT = 2 × MSL = 60秒（Linux默认）

### 8.15 服务端出现大量的TIME_WAIT有哪些原因？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**三大原因：**

| 原因 | 说明 |
|------|------|
| **HTTP没有使用长连接** | 禁用Keep-Alive，服务端主动关闭连接 |
| **HTTP长连接超时** | 超过keepalive_timeout时间，服务端主动关闭 |
| **HTTP长连接请求数达到上限** | 超过keepalive_requests最大值，服务端主动关闭 |

**解决方案：**
1. 开启HTTP长连接（Keep-Alive）
2. 调大keepalive_timeout参数
3. 调大keepalive_requests参数

### 8.17 TCP为什么能实现可靠传输？

**掌握程度：⭐⭐⭐⭐⭐（10星）**

**六大机制：**

| 机制 | 说明 |
|------|------|
| **连接管理** | 三次握手和四次挥手建立可靠连接 |
| **序列号** | 每个字节编号，保证有序和不丢失 |
| **确认应答** | 接收方回传ACK，确认收到数据 |
| **超时重传** | 超时未收到ACK则重发数据 |
| **流量控制** | 根据接收方处理能力调整发送速率 |
| **拥塞控制** | 网络拥堵时减少发送量 |

### 8.19 TCP粘包怎么解决？

### 8.20 TCP的拥塞控制介绍一下？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：**

**拥塞窗口（cwnd）：** 发送方维护的状态变量，动态变化

**发送窗口公式：** 发送窗口 = min(cwnd, 接收窗口)

**四大算法：**

```
┌──────────────────────────────────────────────────────────────┐
│  慢启动（cwnd < ssthresh）                                   │
│  - 每收到一个ACK，cwnd增加1                                  │
│  - 指数增长：1 → 2 → 4 → 8 → 16...                           │
├──────────────────────────────────────────────────────────────┤
│  拥塞避免（cwnd >= ssthresh）                                │
│  - 每收到一个ACK，cwnd增加1/cwnd                             │
│  - 线性增长                                                  │
├──────────────────────────────────────────────────────────────┤
│  拥塞发生（发生丢包）                                        │
│  - 超时重传：cwnd=1, ssthresh=cwnd/2                         │
│  - 快速重传：cwnd=cwnd/2, ssthresh=cwnd                      │
├──────────────────────────────────────────────────────────────┤
│  快速恢复                                                    │
│  - cwnd = ssthresh + 3                                       │
│  - 收到重复ACK，cwnd增加1                                    │
│  - 收到新数据ACK，进入拥塞避免                               │
└──────────────────────────────────────────────────────────────┘
```

### 10.3 Server A和Server B，如何判断两个服务器正常连接？出错怎么办？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**TCP保活机制（KeepAlive）：**

**参数配置：**
```bash
net.ipv4.tcp_keepalive_time=7200    # 保活时间（2小时）
net.ipv4.tcp_keepalive_intvl=75     # 检测间隔（75秒）
net.ipv4.tcp_keepalive_probes=9     # 检测次数（9次）
```

**检测时间：** 7200 + 75×9 = 7875秒（2小时11分15秒）

**检测场景：**

| 场景 | 结果 |
|------|------|
| 对端宕机 | 多次探测无响应，报告连接死亡 |
| 对端宕机并重启 | 收到RST报文，快速发现连接重置 |
| 对端无响应 | 达到探测次数后报告连接死亡 |

**注意：** 需要应用程序设置`SO_KEEPALIVE`选项才能生效。

**替代方案：** 在应用层实现心跳机制（更快速检测）。

## 11. 网络安全

### 11.1 什么是DDoS攻击？怎么防范？

**掌握程度：⭐⭐⭐⭐（8星）**
**考察频次：⭐⭐⭐⭐（7星）**

**答案：**

**DDoS：** 分布式拒绝服务攻击

**原理：**
- 攻击者控制大量僵尸网络（Botnet）
- 同时向目标服务器发送大量请求
- 导致服务器资源耗尽，无法正常服务

**攻击类型：**

| 层级 | 攻击类型 | 特点 |
|------|---------|------|
| 网络层 | UDP反射攻击 | 拥塞网络带宽 |
| 传输层 | SYN Flood、连接数攻击 | 占用连接池资源 |
| 会话层 | SSL连接攻击 | 占用SSL会话资源 |
| 应用层 | HTTP Flood、DNS Flood | 消耗应用处理资源 |

**防范措施：**

| 措施 | 说明 |
|------|------|
| **增强基础设施** | 提升网络带宽和服务器处理能力 |
| **防火墙和IDS** | 配置防火墙规则，入侵检测 |
| **流量清洗** | 使用DDoS防护服务过滤恶意流量 |
| **负载均衡** | 将流量分发到多台服务器 |
| **限流** | 限制单IP请求频率 |
| **CDN** | 使用CDN分散流量 |

### 11.2 SQL注入问题是什么？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：**

**SQL注入：** 攻击者通过在用户输入中注入恶意SQL代码，绕过验证或执行未授权操作。

**示例：**
```sql
-- 正常查询
SELECT * FROM users WHERE name = '张三';

-- 注入攻击
SELECT * FROM users WHERE name = '张三' OR '1'='1';  -- 永真条件
```

**解决方法：**

| 方法 | 说明 |
|------|------|
| **参数化查询** | 使用预编译语句，参数与SQL分离 |
| **输入验证** | 检验输入格式和类型 |
| **转义特殊字符** | 对特殊字符进行转义 |
| **最小权限原则** | 数据库用户只授予必要权限 |
| **使用ORM框架** | 避免直接写SQL语句 |

### 11.3 CSRF攻击是什么？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：**

**CSRF：** 跨站请求伪造

**原理：**
1. 用户登录受信任网站A
2. 攻击者诱导用户访问恶意网站B
3. 网站B自动发起对网站A的请求（携带用户Cookie）
4. 网站A执行了攻击者构造的恶意操作

**解决CSRF的方法：**

| 方法 | 说明 |
|------|------|
| **验证Referer** | 检查请求来源是否合法 |
| **CSRF Token** | 在表单中添加随机Token |
| **双重验证** | 验证码、确认操作等 |
| **SameSite Cookie** | 设置Cookie的SameSite属性 |
| **CORS配置** | 正确配置跨域资源共享 |

### 11.4 XSS攻击是什么？

**掌握程度：⭐⭐⭐⭐⭐（10星）**
**考察频次：⭐⭐⭐⭐⭐（10星）**

**答案：**

**XSS：** 跨站脚本攻击

**三种类型：**

| 类型 | 说明 | 特点 |
|------|------|------|
| **存储型XSS** | 恶意脚本永久存储在服务器 | 最危险，可长期潜伏 |
| **反射型XSS** | 恶意脚本通过URL反射 | 需诱导用户点击 |
| **DOM型XSS** | 客户端脚本修改DOM | 不经过服务器 |

**预防XSS的方法：**

| 方法 | 说明 |
|------|------|
| **输入验证** | 检验用户输入，过滤特殊字符 |
| **输出编码** | HTML转义、URL编码等 |
| **HttpOnly Cookie** | 防止JavaScript读取Cookie |
| **Content Security Policy** | 限制可执行的脚本来源 |
| **避免innerHTML** | 使用textContent代替 |

### 11.5 了解过DNS劫持吗？

**掌握程度：⭐⭐⭐（6星）**
**考察频次：⭐⭐⭐（5星）**

**答案：**

**DNS劫持：** 攻击者篡改DNS解析结果，将用户引导到恶意网站

**原理：**
- 攻击者在用户查询DNS时
- 返回伪造的IP地址
- 用户被重定向到攻击者控制的网站

**防范措施：**

| 方法 | 说明 |
|------|------|
| **使用HTTPS** | 加密通信，防止篡改 |
| **DNS over HTTPS** | 使用加密的DNS查询 |
| **定期检查hosts文件** | 防止本地被篡改 |
| **使用可信DNS** | 选择安全的DNS服务商 |
| **DNSSEC** | DNS安全扩展，验证响应真实性 |

## Agent 开发相关网络补充

这部分不是传统计网八股的核心章节，但对 `Agent` 应用研发非常常见，尤其是平台、工具调用、流式输出和集成场景。

### 1. 什么是 SSE？

**面试可讲定义：**

SSE（Server-Sent Events）是一种基于 HTTP 的单向流式推送机制，服务端可以持续向客户端发送文本事件流，浏览器或前端客户端按事件增量接收。

**关键点：**

- 单向：服务端 -> 客户端
- 底层还是 HTTP 连接
- 很适合文本增量输出
- 常见 `Content-Type` 是 `text/event-stream`

**为什么 Agent 场景常用？**

- 模型输出天然是增量 token
- 前端可以边收边渲染
- 用户感知延迟更低
- 实现通常比 WebSocket 更轻

**一句话表达：**

“在 AI 应用里，SSE 很常用来做模型流式输出，因为它足够轻、和 HTTP 生态兼容，而且非常适合 token-by-token 或 chunk-by-chunk 的增量展示。”

### 2. SSE 和 WebSocket 的区别

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 方向 | 单向推送 | 双向通信 |
| 协议基础 | HTTP | 独立升级协议 |
| 场景 | 模型流式输出、状态通知 | 强交互、双向实时协作 |
| 实现复杂度 | 较低 | 较高 |

**面试答法：**

如果只是服务端持续输出模型结果，优先用 SSE；如果需要前后端高频双向消息交互，再考虑 WebSocket。

### 3. AI 流式消息传输为什么重要？

**原因：**

- 降低首 token 等待焦虑
- 提升用户感知速度
- 便于边生成边消费
- 更适合长回答、Agent 多步执行和日志展示

**你可以怎么讲：**

“AI 应用里，流式传输不只是体验优化，它还影响链路设计。因为很多时候前端不仅要展示最终答案，还要展示生成过程、工具调用状态或者中间进度，所以流式输出经常和 trace、事件、状态流一起出现。”

### 4. 流式传输常见追问

**Q：为什么流式输出比一次性返回更复杂？**

答：

因为它涉及连接保持、分块发送、前端增量渲染、取消请求、异常中断恢复，以及有时还要区分“模型文本”“工具事件”“状态事件”这些不同类型的流。

**Q：流式输出时最常见的工程问题是什么？**

答：

- 前端把部分内容当完整内容处理
- 中断后状态不一致
- 多事件类型混在一个流里不好解析
- 代理层或网关层对长连接超时不友好

### 5. 什么是 MCP？

**面试可讲定义：**

MCP（Model Context Protocol）可以理解成模型或 Agent 和外部工具/资源之间的标准化上下文与能力接入协议。

**你可以这样讲：**

“MCP 的核心价值是把工具、资源和模型之间的接入方式做标准化，让 Agent 不必为每个外部系统都重新定制一套集成逻辑。”

### 6. MCP 和普通 Tool Calling 的区别

**普通 Tool Calling：**

- 更像单个工具函数调用
- 接口通常由业务自己定义

**MCP：**

- 更强调统一协议
- 不只是函数，还有资源、上下文和能力发现
- 更适合平台化、多工具、多来源接入

**一句话表达：**

“Tool Calling 解决的是‘调一个工具’，MCP 更想解决的是‘如何用统一协议接入一类外部能力’。”

### 7. MCP 和网络基础的关系

你不需要把 MCP 讲成网络协议实现细节，但要知道它常落在：

- `stdio`
- `HTTP`
- `SSE`

这样的传输层之上。

也就是说：

- `MCP` 管的是能力接入协议
- `HTTP / SSE / stdio` 管的是传输层承载方式

### 8. 什么是 ACP？

**面试可讲定义：**

ACP（Agent Communication Protocol）更偏 Agent-to-Agent 通信协议，它解决的是多个 Agent 之间如何用标准方式交换消息、能力和任务状态。

**和 MCP 的区别：**

- `MCP`：接工具 / 资源
- `ACP`：Agent 和 Agent 协作

**为什么你需要知道它？**

因为多 Agent 系统越来越常见，面试官有时会顺着 `MCP` 再问：

- 如果不是接工具，而是多个 Agent 协作呢？
- 它们之间靠什么协议说话？

这时候你就可以把 `ACP / A2A` 提出来。

### 9. 面试里怎么把这些和项目连起来

你可以这样收口：

“在 Agent 平台里，网络知识不再只是 TCP/HTTP 八股，还经常落到 SSE 流式输出、事件传输、工具接入和协议标准化这些层面。像流式消息适合做模型输出和状态展示，MCP 更适合工具接入，ACP / A2A 更适合多 Agent 协作。”
