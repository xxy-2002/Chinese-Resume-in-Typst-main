# MySQL 与 Redis 面试题·融合精简版

> 把数据库、缓存、事务、复制和高并发场景放在一条数据链路中理解。每题附 **Key words**。

## 一、数据模型与读写路径

### Q01：MySQL 和 Redis 各自解决什么问题？为什么通常一起使用？

**答案：**

MySQL 是持久化关系型数据库，擅长事务、一致性查询和复杂条件检索；Redis 是内存数据结构服务，擅长低延迟读写、临时状态、缓存、计数、限流和消息协调。

常见模式是 MySQL 作为事实来源，Redis 缓存热点数据或承载短生命周期状态。Redis 不应默认成为唯一真相：要设计失效、回填、持久化、降级和数据修复路径。

**Key words:** MySQL、Redis、事实来源、缓存、持久化、低延迟、降级、数据修复

### Q02：一条 SQL 的执行与一次 Redis 访问分别经过什么路径？

**答案：**

SQL 通常经过连接器、解析器、优化器、执行器和 InnoDB；InnoDB 从 Buffer Pool 或磁盘读取索引/数据页，修改时生成 undo、redo，并在提交时写 binlog。

Redis 请求由事件循环读取、解析命令、执行命令并返回结果；大多数命令在主线程顺序执行，因此单条慢命令、大 key 或阻塞命令会影响其他请求。

两者都需要连接池、超时、慢日志和容量监控；“内存数据库一定快”不代表业务链路一定快。

**Key words:** SQL 执行链路、优化器、执行器、InnoDB、Buffer Pool、Redis 事件循环、慢日志、连接池

### Q03：索引为什么使用 B+ 树？聚簇索引、二级索引和回表是什么？

**答案：**

InnoDB 的 B+ 树扇出高、树高低，适合磁盘页访问和范围扫描。聚簇索引叶子节点保存完整行数据；二级索引叶子节点保存二级键和主键值，查询所需列不在二级索引中时，要根据主键再查聚簇索引，这就是回表。

覆盖索引让查询字段都来自同一二级索引，可避免回表。主键应短、稳定、尽量递增，减少聚簇索引页分裂和二级索引体积。

**Key words:** B+ 树、聚簇索引、二级索引、回表、覆盖索引、主键、页分裂、范围查询

### Q04：联合索引、最左前缀和索引失效怎么解释？

**答案：**

联合索引按定义顺序排序，如 (a,b,c) 可有效支持 a、a+b、a+b+c 的连续前缀。等值条件通常可继续利用后续列；范围条件后的列往往不能继续用于缩小索引扫描范围，但仍可能用于覆盖或过滤。

对列做函数/隐式转换、前置通配符模糊查询、低选择性条件、错误的排序分组和不匹配的联合索引都可能导致索引收益低。不要凭规则猜，使用 EXPLAIN、慢日志和真实数据验证。

**Key words:** 联合索引、最左前缀、选择性、范围查询、隐式转换、EXPLAIN、慢查询

### Q05：Redis 的核心数据结构如何按场景选择？

**答案：**

String 适合简单缓存、计数和分布式锁 token；Hash 适合对象字段；List 适合简单队列；Set 适合去重和集合运算；ZSet 适合排名和按分数范围检索；Bitmap/HyperLogLog/Geo 适合特定统计和地理场景。

结构选择要看访问模式、单 key 大小、过期策略、原子操作需求和集群分片。不要把一个不断膨胀的大 JSON 或大集合塞进单 key。

**Key words:** String、Hash、List、Set、ZSet、Bitmap、HyperLogLog、大 key、过期

## 二、事务、一致性与锁

### Q06：ACID、隔离级别和 MVCC 如何串起来？

**答案：**

ACID 分别是原子性、一致性、隔离性、持久性。隔离级别在脏读、不可重复读和幻读之间权衡；InnoDB 默认可重复读，通过 MVCC 让普通一致性读根据 Read View 和 undo 版本链读取快照。

当前读，如 UPDATE、DELETE、SELECT FOR UPDATE，会读取最新版本并加锁。MVCC 不能替代所有锁：写冲突、唯一性和范围保护仍需要锁机制。

**Key words:** ACID、隔离级别、MVCC、Read View、undo log、一致性读、当前读、幻读

### Q07：InnoDB 锁、间隙锁和死锁如何排查？

**答案：**

InnoDB 有记录锁、间隙锁和 next-key lock，也有表级 MDL、意向锁等。索引决定锁的范围：命中精确索引通常锁得更小，缺索引的更新/范围扫描可能扩大锁定范围。

死锁是多个事务相互等待，数据库会选择代价较小的事务回滚。优化方式是固定访问顺序、缩短事务、补齐索引、拆分批处理和捕获死锁后有限重试；不能只靠增大锁等待超时。

**Key words:** 记录锁、间隙锁、next-key lock、MDL、死锁、锁等待、索引、事务顺序

### Q08：redo、undo、binlog、WAL 和两阶段提交分别解决什么问题？

**答案：**

undo 用于回滚和 MVCC；redo 记录页修改以支持崩溃恢复，遵循 WAL，先保证日志再异步刷脏页；binlog 记录逻辑变更，用于复制和恢复。两阶段提交用同一个 XID 协调 redo prepare 和 binlog，避免两份日志不一致。

doublewrite 处理数据页部分写坏的问题，不能用 redo 完全替代。持久性参数是性能与数据丢失窗口的权衡，应按业务 RPO 选择。

**Key words:** undo log、redo log、binlog、WAL、两阶段提交、XID、doublewrite、RPO、崩溃恢复

### Q09：Redis 原子性、事务和 Lua 脚本有什么边界？

**答案：**

单条 Redis 命令是原子的；MULTI/EXEC 将命令序列顺序执行，但不提供像 MySQL 那样的隔离回滚语义。Lua 脚本可以把读改写放进一次原子执行中，适合库存扣减、限流和状态转换。

脚本必须短小、可预测，避免长循环和阻塞操作；分布式业务一致性仍需要幂等、消息可靠投递、补偿或事务外盒等机制。

**Key words:** Redis 原子性、MULTI、EXEC、Lua、库存扣减、限流、幂等、补偿

## 三、缓存与高并发

### Q10：Cache Aside 如何保证 MySQL 与 Redis 的最终一致性？

**答案：**

常用 Cache Aside：读时先查缓存，未命中查数据库后回填；写时先更新数据库，再删除缓存。删除而非直接更新缓存可减少并发计算和写入顺序问题，但仍存在短暂不一致。

关键点是删除失败重试、消息/订阅 binlog 做异步修复、设置合理 TTL、回填时防止旧值覆盖新值。强一致读不能只依赖缓存，应读主库或使用版本校验。

**Key words:** Cache Aside、先更新数据库再删缓存、TTL、删除重试、binlog、最终一致性、版本号

### Q11：缓存穿透、击穿、雪崩、热 key 和大 key 如何区分和处理？

**答案：**

- 穿透：请求不存在的数据，使用参数校验、布隆过滤器和空值缓存；
- 击穿：热点 key 失效瞬间大量回源，用互斥重建、逻辑过期或提前刷新；
- 雪崩：大量 key 同时失效或缓存整体故障，用过期时间打散、多级缓存、限流和降级；
- 热 key：单 key 流量过高，用本地缓存、读副本和拆分；
- 大 key：单次操作耗时/网络包大，用拆分、scan、渐进删除和大小监控。

**Key words:** 缓存穿透、击穿、雪崩、热 key、大 key、布隆过滤器、逻辑过期、降级

### Q12：Redis 分布式锁如何正确实现？什么时候不该用？

**答案：**

锁要使用 SET key token NX PX ttl，释放时通过 Lua 比较 token 后删除，防止误删别人的锁。业务执行时间可能超过 TTL，需要续租、超时控制和幂等/围栏令牌；网络分区下不能把它当绝对一致性锁。

若数据库唯一约束、乐观锁、队列串行化或单机互斥已经足够，应优先用更简单的机制。分布式锁保护的是并发协调，不替代事务和业务幂等。

**Key words:** 分布式锁、SET NX PX、token、Lua、续租、围栏令牌、网络分区、幂等

### Q13：秒杀/高并发扣库存如何避免超卖？

**答案：**

入口先做鉴权、限流和排队；Redis 可做预扣减或资格校验，订单异步写入消息队列；数据库用条件更新，例如库存大于零才扣减，或用版本号保证最终正确性。消费者要幂等，订单号/请求号要唯一，超时订单需要补偿库存。

缓存预扣只能削峰，最终库存真相仍需在数据库或可靠事务边界确认。

**Key words:** 秒杀、限流、排队、预扣减、条件更新、乐观锁、消息队列、幂等、补偿

## 四、复制、扩展与调优

### Q14：MySQL 主从复制、延迟和分库分表怎么回答？

**答案：**

主库写 binlog，从库拉取并写 relay log，再由 SQL/applier 线程回放。长事务、大批量写、从库资源不足或网络抖动会产生复制延迟。读写分离要接受旧读，关键读走主库或等待位点。

单库瓶颈先通过索引、SQL、归档、读副本和垂直拆分解决；确需水平分片时选择分片键、全局 ID、路由、跨分片查询和扩容方案。分库分表会提高运维和事务复杂度。

**Key words:** 主从复制、binlog、relay log、复制延迟、读写分离、分库分表、分片键、全局 ID

### Q15：Redis 持久化、主从、哨兵和 Cluster 的取舍是什么？

**答案：**

RDB 是时间点快照，恢复快但可能丢最后一段数据；AOF 追加写、数据更完整但体积和恢复成本更高，可配置 fsync 策略。主从复制提升读能力和容灾，但默认是异步复制。

Sentinel 负责监控和故障转移；Cluster 按槽分片扩容并提供部分高可用。跨槽多 key 操作、热点槽、迁移和客户端重定向是 Cluster 的常见工程边界。

**Key words:** RDB、AOF、fsync、主从复制、Sentinel、Cluster、hash slot、故障转移

### Q16：SQL 和 Redis 性能问题应该怎样排查？

**答案：**

MySQL 从慢日志、QPS、连接数、锁等待、Buffer Pool、EXPLAIN、扫描行数和磁盘 I/O 入手；Redis 从慢日志、延迟、命令复杂度、内存碎片、命中率、bigkey/hotkey、网络和持久化 fork 成本入手。

先确认是 CPU、I/O、锁、网络、连接池还是下游排队，再做最小改动验证。优化完成后对照基线复测 p95/p99 和错误率。

**Key words:** 慢日志、EXPLAIN、锁等待、Buffer Pool、Redis latency、命中率、bigkey、hotkey、p99
