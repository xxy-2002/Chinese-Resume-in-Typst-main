## 一、模型基础与架构

### Q01：什么是大语言模型？预训练解决什么问题？

**答案：**

大语言模型通过在大量文本或多模态数据上学习 token 的条件分布，获得语言理解、生成、知识记忆和模式归纳能力。预训练通常以自回归 next-token prediction 或掩码建模为目标，学到通用表示和生成能力。

预训练后的模型“会生成”，但不一定遵循指令、调用工具或符合业务格式，所以还需要指令微调、偏好对齐和应用层约束。

**Key words:** LLM、token、条件分布、预训练、自回归、next-token、指令遵循、对齐

### Q02：Transformer 为什么适合大模型？

**答案：**

Transformer 用自注意力让每个 token 直接聚合上下文，配合位置编码、前馈网络、残差连接和 LayerNorm 构成深层网络。训练阶段序列位置可以并行计算，相比 RNN 更适合 GPU/TPU。

代价是注意力的序列长度成本较高，长上下文会带来显存、计算和 KV Cache 压力；工程上会通过 FlashAttention、稀疏注意力、分块和缓存优化。

**Key words:** Transformer、自注意力、位置编码、FFN、残差、LayerNorm、并行训练、长上下文

### Q03：注意力、QKV 和 KV Cache 如何解释？

**答案：**

Query 表示当前查询，Key 用于匹配相关性，Value 携带被聚合的信息；注意力权重由 Q 与 K 的相似度计算，再加权求和 V。

自回归生成时，历史 token 的 K/V 不需要每步重算，可以缓存起来，这就是 KV Cache。它降低重复计算，但会随 batch、层数、序列长度和 head 维度增长，成为推理显存的重要部分。

**Key words:** Attention、Q/K/V、Self-Attention、KV Cache、自回归、显存、序列长度

### Q04：Dense、Sparse 和 MoE 有什么区别？

**答案：**

Dense 模型每个 token 都经过全部参数；Sparse/MoE 模型只激活部分专家。MoE 通常由 Router 为 token 选择 top-k 专家，再将专家输出聚合。

MoE 可以扩大总参数量而控制每 token 的计算量，但会引入路由负载不均、通信、专家容量和训练稳定性问题。不能只看总参数量，要看激活参数、吞吐、显存和部署通信。

**Key words:** Dense、Sparse、MoE、Router、Top-k、专家、激活参数、负载均衡、通信

### Q05：模型能力、上下文和知识库分别解决什么问题？

**答案：**

模型参数提供通用能力和训练时知识；上下文窗口提供当前请求可见的信息；知识库/RAG 提供可更新、可追溯的外部证据。把所有信息都塞进模型或上下文都会带来更新、成本和可靠性问题。

实际系统通常组合三者：模型负责理解和生成，RAG 提供事实，应用代码负责权限、状态和确定性规则。

**Key words:** 模型参数、上下文窗口、知识库、RAG、事实、更新、权限、确定性规则

## 二、训练、微调与对齐

### Q06：SFT 是什么？数据如何构造？

**答案：**

SFT 在预训练模型上使用高质量指令-回答或多轮对话继续训练，让模型学习任务格式、表达风格、工具调用和业务流程。训练通常只对 assistant 输出计算 loss，避免模型被用户输入主导。

数据质量比盲目扩大数量重要：要覆盖任务分布、困难样例、拒答边界、工具错误和长短上下文，并去重、脱敏、划分训练/验证/回归集。

**Key words:** SFT、指令数据、对话数据、assistant loss、工具调用、数据质量、回归集

### Q07：LoRA/QLoRA 为什么适合工程实践？

**答案：**

LoRA 冻结基座参数，只训练低秩增量矩阵；QLoRA 再结合量化降低显存。它减少可训练参数、显存和多版本适配成本，适合领域、格式和行为微调。

LoRA 不是免费午餐：rank、目标层、数据质量、量化误差和合并/部署方式都会影响效果。它不能替代检索、工具和业务规则。

**Key words:** LoRA、QLoRA、低秩矩阵、冻结参数、量化、rank、适配器、显存

### Q08：RLHF、DPO、GRPO 怎么区分？

**答案：**

- RLHF 是完整偏好对齐路线，常包含偏好数据、奖励模型和 PPO 等策略优化；
- DPO 直接用 chosen/rejected 偏好对优化策略，不必单独在线训练奖励模型；
- GRPO 是一类相对轻量的组内相对奖励优化方法，常用于可验证推理或 Agent 轨迹。

面试时要说明训练信号不同：偏好对、奖励模型或环境/结果反馈；是否需要 rollout、价值模型和信用分配。

**Key words:** RLHF、DPO、GRPO、偏好对、Reward Model、PPO、rollout、环境奖励

### Q09：Agentic RL 与普通 SFT/DPO 的区别是什么？

**答案：**

SFT/DPO 多围绕单轮或短序列输出优化；Agentic RL 把多步任务看成环境交互，动作可以是工具调用、路由、规划或终止，奖励来自结果和过程。

难点在于轨迹长、奖励稀疏、工具有副作用、环境噪声大和信用分配困难。工程上应先用规则、trace 和 eval 找到能力缺口，再决定是否值得上 RL。

**Key words:** Agentic RL、轨迹、环境、动作空间、稀疏奖励、信用分配、工具调用、Eval

## 三、推理、部署与成本

### Q10：一次模型推理的主要性能指标有哪些？

**答案：**

首 token 延迟（TTFT）反映排队和 prefill，生成速度（tokens/s）反映 decode，端到端延迟还包括网络、工具和后处理。还要看并发、吞吐、显存、错误率、上下文长度和单位请求成本。

优化不能只追求 tokens/s：用户体验可能更关注 TTFT，长任务更关注总时延和稳定性。

**Key words:** TTFT、prefill、decode、tokens/s、吞吐、并发、显存、端到端延迟、成本

### Q11：vLLM 和 PagedAttention 为什么能提高推理效率？

**答案：**

自回归服务中不同请求的 KV Cache 长度不同，传统连续显存分配容易产生碎片和浪费。PagedAttention 把 KV Cache 按页管理，按需分配和共享，提升显存利用率与批处理能力。

vLLM 还结合 continuous batching、调度和高效 kernel。实际收益取决于模型、上下文长度、并发、量化、GPU 和请求分布，必须压测验证。

**Key words:** vLLM、PagedAttention、KV Cache、显存碎片、continuous batching、kernel、压测

### Q12：模型显存和部署容量如何粗略估算？

**答案：**

权重显存约等于参数量乘每参数字节数；推理还要加 KV Cache、激活、框架开销和通信缓冲。训练则额外需要梯度、优化器状态和激活保存，通常远大于推理。

容量规划要根据最大上下文、并发、batch、量化、GPU 显存和副本数估算，并留出峰值与故障转移余量。

**Key words:** 参数量、权重、精度、FP16、INT8、KV Cache、激活、优化器状态、容量规划

### Q13：模型选择如何平衡效果、延迟、成本和隐私？

**答案：**

先按任务拆分：简单分类/抽取可用小模型，复杂推理和规划再用强模型；敏感数据、稳定低延迟和高吞吐场景可评估私有部署，开放域或峰值弹性可用托管 API。

用同一评测集比较成功率、事实性、工具正确性、TTFT、总延迟、token 成本和故障率，并通过路由、缓存、批处理和降级控制成本。

**Key words:** 模型选型、效果、延迟、成本、隐私、小模型、私有部署、路由、降级

## 四、RAG、Memory 与工具接入

### Q14：RAG 的完整链路是什么？瓶颈在哪里？

**答案：**

离线链路负责解析、清洗、切分、embedding 和索引；在线链路负责 query 改写、过滤、多路召回、重排、上下文拼装和生成。

瓶颈可能在切分丢语义、召回漏证据、重排慢、上下文超长、数据过期或权限过滤错误。优化要分别看 Recall、Precision、Faithfulness、延迟、成本和新鲜度。

**Key words:** RAG、切分、embedding、query rewrite、多路召回、rerank、上下文、召回率、事实性

### Q15：向量检索、关键词检索和重排如何组合？

**答案：**

向量检索适合语义相似，关键词/BM25 适合专有名词、编号和精确匹配；混合召回先扩大候选集，再用 cross-encoder 或轻量模型重排，最后按权限、时间和来源过滤。

重排提高相关性但增加延迟和成本，要通过候选数量、模型大小、缓存和分层策略平衡。

**Key words:** 向量检索、BM25、混合召回、候选集、Rerank、权限过滤、延迟、成本

### Q16：Memory 为什么不能只依赖上下文窗口？

**答案：**

上下文有长度、成本和噪声限制；长期对话直接累加会让重要信息被淹没。应区分短期会话、工作记忆、长期用户事实和共享任务状态。

记忆写入需要筛选、摘要、去重、权限和过期；读取需要按相关性和作用域召回，不能把所有历史无条件塞给模型。

**Key words:** 短期记忆、长期记忆、工作记忆、摘要、去重、作用域、过期、隐私

### Q17：Tool Calling、MCP 和 Skill 有什么区别？

**答案：**

Tool Calling 是模型输出结构化调用某个函数/API；MCP 强调以统一协议发现和接入工具、资源与上下文；Skill 是包含说明、规则、参考资料和脚本的可复用做事能力。

一句话：Tool 是能力点，MCP 是标准化接入方式，Skill 是可复用能力单元。三者都要配合 schema、权限、超时、审计和错误处理。

**Key words:** Tool Calling、MCP、Skill、schema、能力发现、资源、权限、审计

### Q18：SSE、WebSocket 和流式 Agent 输出怎么设计？

**答案：**

SSE 基于 HTTP 单向推送，适合 token、工具状态和进度流；WebSocket 支持双向实时交互，适合协作和高频双向消息。Keep-Alive 只是复用 HTTP 连接，不等于服务端主动推送。

流式接口要定义事件类型、序号、心跳、取消、断线恢复和终态；客户端断开后服务端必须取消模型和工具任务，避免后台继续消耗资源。

**Key words:** SSE、WebSocket、Keep-Alive、事件流、序号、心跳、取消、断线恢复

## 五、Agent 编排与生产化

### Q19：什么是 Agent？它与普通 Prompt 的区别是什么？

**答案：**

Prompt 更像一次输入输出；Agent 围绕目标持续决策、调用工具、读取状态、处理结果并执行多步任务。Agent 的可靠性来自模型、状态机、工具、护栏、预算和观测共同作用，而不是只靠一段长 prompt。

生产系统应把确定性步骤固定，把需要判断的局部交给模型，并设置最大步数、成本和时间预算。

**Key words:** Agent、Prompt、目标、决策、工具、状态、工作流、预算、Guardrail

### Q20：Harness、Runtime、Trace、Eval 和 Guardrail 分别是什么？

**答案：**

- Harness：组织任务、上下文、工具、文件、权限和验证的执行底座；
- Runtime：实际调度任务、工具、状态、并发和异常；
- Trace：记录一次执行的模型、工具、状态、错误和耗时；
- Eval：用可重复数据判断结果、过程、成本和安全是否变好；
- Guardrail：限制危险工具、越权访问、输出格式和敏感数据的规则。

这些能力一起构成“可执行、可观测、可评测、可治理”的 Agent 系统。

**Key words:** Harness、Runtime、Trace、Eval、Guardrail、状态、权限、可观测性

### Q21：Agentic Workflow 和传统 Workflow 如何组合？

**答案：**

传统 Workflow 的步骤固定、可预测、易测试；Agentic Workflow 允许模型在有限节点选择工具、路径或下一步。生产上应采用混合模式：流程骨架固定，模型负责局部判断，状态机负责合法转移。

每一步需要输入输出 schema、重试策略、停止条件和人工接管，否则模型自由度会导致成本、延迟和失败路径不可控。

**Key words:** Agentic Workflow、传统 Workflow、状态机、schema、停止条件、人工接管、混合模式

### Q22：Multi-Agent 为什么不是简单多开几个模型？

**答案：**

多 Agent 需要角色边界、路由、通信协议、共享状态、结果聚合和停止条件。常见模式有 planner/executor、supervisor/worker、proposer/verifier。

要限制 Agent 数量、token、工具调用次数和总耗时；能用单 Agent 解决时不要为了“多智能体”增加复杂度。用 trace 评估路由正确率、重复劳动、任务成功率和成本。

**Key words:** Multi-Agent、planner、executor、supervisor、worker、verifier、路由、聚合、成本

### Q23：Agent 工具调用如何保证安全和可靠？

**答案：**

工具定义要包含 schema、权限、超时、速率和副作用说明；执行前校验参数和授权，危险操作进入沙箱或人工确认；执行后记录结果、耗时、trace 和可重试性。

模型输出是不可信输入，不能直接拼 SQL、Shell 或文件路径。外部副作用工具必须使用幂等键、条件更新和补偿。

**Key words:** Tool Use、schema、权限、沙箱、人工确认、不可信输入、幂等键、补偿

### Q24：Agent 系统如何做 Trace-first Eval？

**答案：**

同时评估最终答案和执行轨迹：任务完成率、工具选择、参数正确性、步骤数、延迟、token 成本、错误重试、护栏触发和人工接管率。

数据拆成开发集、holdout 集和回归集；规则检查与模型评审结合。每次修改模型、prompt、工具或路由都重放代表性 trace，把 badcase 转成测试和护栏。

**Key words:** Trace-first Eval、开发集、holdout、回归、工具正确性、成本、badcase、重放

### Q25：Agent 生产环境最容易出现哪些问题？如何治理？

**答案：**

常见问题包括上下文膨胀、工具超时、重复副作用、模型幻觉、流式断连、任务泄漏、成本失控和数据越权。治理措施包括上下文压缩、超时取消、幂等/补偿、权限和沙箱、预算、限流、降级、审计和回归评测。

上线前明确 SLO、容量、故障转移和人工接管；上线后用日志、指标和 trace 持续定位问题，不只看最终回答分数。

**Key words:** 上下文压缩、超时、取消、幂等、沙箱、预算、限流、降级、审计、SLO

### Q26：如何把大模型与 Agent 知识落到项目介绍中？

**答案：**

按“业务目标 → 模型能力 → Agent 流程 → 工具/记忆/RAG → 评测 → 工程指标”讲。先说明为什么需要模型，再说明哪些步骤固定、哪些步骤交给模型，最后给出成功率、延迟、成本、稳定性或人工效率变化。

不要只报框架名；说明自己解决了什么 badcase、如何观测和验证，以及为什么选择当前模型、协议和部署方式。

**Key words:** 业务目标、模型能力、Agent 流程、RAG、Memory、Tool、Eval、延迟、成本、稳定性
