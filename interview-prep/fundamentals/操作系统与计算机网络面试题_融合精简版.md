## 一、执行、进程与并发

### Q01：用户态、内核态、系统调用、中断和异常是什么关系？

**答案：**

- **用户态**权限低，普通程序只能执行非特权指令、访问自己的用户空间；**内核态**权限高，可以管理页表、进程、设备和网络协议栈。
- 用户程序需要文件、网络、进程等内核资源时，通过**系统调用**进入内核。系统调用是同步陷入，内核保存现场、切到内核栈，完成处理后返回用户态。
- **中断**通常由外部设备异步触发，例如网卡收到数据、磁盘完成读写；**异常**由当前指令同步触发，例如除零、非法访问、缺页。
- 从网络角度看，网卡中断把数据交给内核协议栈；应用再通过 read、recv 或 epoll_wait 取走数据。

**Key words:** 用户态、内核态、系统调用、特权指令、中断、异常、内核栈、同步/异步

### Q02：进程、线程和协程如何区分？为什么进程下面还要有线程？

**答案：**

| 维度 | 进程 | 线程 | 协程 |
| --- | --- | --- | --- |
| 主要角色 | 资源隔离与分配单位 | 内核调度与执行单位 | 用户态调度的轻量任务 |
| 地址空间 | 独立 | 同进程共享 | 通常共享所属线程/进程地址空间 |
| 切换成本 | 通常最高 | 低于进程 | 保存少量寄存器和栈，通常最低 |
| 并发来源 | 多进程 | 多核并行、内核调度 | 协作式让出，不能自动突破单线程 CPU |

线程让多个执行流共享代码、堆、全局变量和文件描述符，既能并发处理任务，又避免多进程 IPC 和地址空间切换的成本。代价是共享数据带来竞态、死锁，以及一个线程的未处理致命错误可能终止整个进程。协程适合大量 I/O 等待，但必须配合非阻塞 I/O 或事件循环。

**Key words:** 进程隔离、线程共享、协程、内核调度、用户态调度、并发、并行、资源分配

### Q03：进程切换和线程切换到底切换什么？为什么线程通常更快？

**答案：**

切换的核心是保存当前执行流的 CPU 上下文，再恢复下一个执行流的上下文，至少包括程序计数器、通用寄存器、栈指针和调度状态。

- **线程切换**：同一进程内通常复用页表、代码、堆和文件表，主要切换寄存器、内核栈和线程控制块。
- **进程切换**：通常还要切换地址空间和页表，可能造成 TLB 失效，并改变进程级资源上下文。
- 调度器选择就绪任务后完成保存、选择、恢复、返回执行。切换不是免费的，线程过多会让 CPU 时间消耗在调度和缓存失效上。

严格来说，同一地址空间的不同进程或特殊内核优化可能减少部分开销，所以“线程一定比进程快”不是绝对定律。

**Key words:** 上下文切换、PCB、TCB、程序计数器、寄存器、内核栈、页表、TLB、调度器

### Q04：进程有哪些状态？调度算法怎么影响响应和吞吐？

**答案：**

常见状态是**新建、就绪、运行、阻塞、终止**：等待 CPU 是就绪，等待 I/O 或事件是阻塞；事件完成后回到就绪，时间片用完可能从运行回到就绪。

常见调度策略：

- **先来先服务（FCFS）**：简单公平，但长作业可能拖慢所有短作业。
- **短作业优先（SJF）/高响应比优先**：改善平均等待时间，但需要估计执行时间。
- **时间片轮转（RR）**：交互响应好；时间片太小会增加切换，太大又接近 FCFS。
- **优先级、多级反馈队列**：兼顾重要任务和交互任务，需防止低优先级任务饥饿。

服务器中常见做法是事件循环负责 I/O 就绪，线程池或任务队列负责 CPU/阻塞工作，避免阻塞事件循环。

**Key words:** 就绪态、运行态、阻塞态、时间片、FCFS、SJF、RR、多级反馈队列、饥饿

### Q05：进程间通信和线程间同步有哪些方式？如何选择？

**答案：**

- **管道/命名管道**：字节流，匿名管道常用于有亲缘关系的进程，命名管道可用于无亲缘关系进程。
- **消息队列**：内核按消息组织数据，适合异步、带类型的通信。
- **共享内存**：多个进程映射同一物理页，拷贝少、吞吐高，但必须搭配互斥锁、信号量或无锁协议。
- **信号**：发送事件通知，不适合承载大量业务数据；**信号量**是同步/资源计数工具，不要和信号混淆。
- **Socket**：既可用于本机进程，也可跨主机通信；网络服务最终也通过文件描述符读写。
- 线程共享地址空间，常用互斥锁、条件变量、读写锁、自旋锁和信号量；生产者消费者通常用“互斥锁 + 条件变量”。

高吞吐本机通信可以考虑共享内存；需要边界、权限和跨机器能力时优先使用消息或 Socket。

**Key words:** IPC、管道、消息队列、共享内存、Socket、信号、信号量、条件变量、生产者消费者

### Q06：为什么并发访问要加锁？互斥锁、自旋锁、读写锁和乐观锁怎么选？

**答案：**

多个执行流至少一个写共享数据时会出现**竞态条件**，导致丢更新、读到中间状态或数据结构损坏。锁要保护的是不变量和临界区，而不是盲目包住所有代码。

- **互斥锁**：抢不到时休眠，适合临界区不短或竞争较强的场景。
- **自旋锁**：抢不到时忙等，适合多核、临界区极短且不允许睡眠的场景；单核或长临界区会浪费 CPU。
- **读写锁**：读共享、写独占，适合读多写少；仍需关注写者饥饿。
- **原子操作/CAS**：适合简单状态或计数更新，复杂不变量仍需要锁。
- **乐观锁**：先读后用版本号/CAS 校验，冲突少时吞吐高；**悲观锁**先互斥再操作，冲突多时更稳。

锁的顺序应全局一致，且尽量缩短持锁时间，避免把网络、磁盘等阻塞操作放进临界区。

**Key words:** 竞态条件、临界区、互斥锁、自旋锁、读写锁、CAS、乐观锁、悲观锁、原子性

### Q07：死锁的四个必要条件是什么？如何避免？

**答案：**

死锁同时满足：**互斥、持有并等待、不可剥夺、环路等待**。最实用的工程方法是给资源建立全局顺序，所有线程按同一顺序加锁；也可以一次性申请资源、缩短持有时间、设置超时并在失败时回滚。

**银行家算法**在分配前模拟资源请求，只有分配后仍存在让所有进程完成的安全序列才批准，适合理论分析，在线服务较少直接使用。检测到死锁后可中止任务、释放资源或重启故障实例，但这属于补救而非预防。

**Key words:** 死锁、互斥、持有并等待、不可剥夺、环路等待、锁顺序、超时、银行家算法、安全序列

## 二、内存、中断与 I/O

### Q08：虚拟内存、页表、TLB 和缺页异常如何串起来？

**答案：**

程序使用的是虚拟地址，MMU 按页把它转换成物理地址。虚拟地址可拆成**虚拟页号 + 页内偏移**；页表把虚拟页号映射到物理页框，偏移保持不变。TLB 缓存热点页表项，命中时无需访问多级页表。

页表项还记录存在位、读写执行权限和脏位。访问不存在或无权限的页会触发**缺页/保护异常**，内核检查访问是否合法：合法时分配或换入物理页、更新页表后重试；非法时向进程发送错误信号。物理内存不足时，内核可能回收文件页或把匿名页换出，极端情况下触发 OOM。

页面置换常见有 OPT（理论最优）、FIFO、LRU 和 Clock；生产系统通常用近似 LRU 的机制，不能把“缺页”简单理解成程序一定出错。

**Key words:** 虚拟内存、物理内存、分页、页表、MMU、TLB、缺页异常、权限位、Swap、OOM、LRU

### Q09：fork 为什么快？Copy-on-Write 是怎么工作的？

**答案：**

fork 创建子进程时复制进程控制信息、页表和文件描述符引用，但父子进程先共享物理页。共享页被标记为只读；任一方写入时触发写保护异常，内核复制该页、更新对应页表，再让写操作继续，这就是**写时复制（COW）**。

因此 fork 后立即 exec 时通常无需复制大量用户数据；但大量写入会产生真实复制成本。文件描述符是引用计数对象，父子进程可能共享同一个打开文件描述的偏移和状态，不能简单理解为“完全独立”。

**Key words:** fork、COW、写时复制、页表、共享物理页、写保护异常、exec、文件描述符

### Q10：进程内存布局、堆栈和 malloc/brk/mmap 有什么关系？内存不足怎么办？

**答案：**

典型用户空间从低地址到高地址可见代码段、只读数据、已初始化/未初始化数据、堆、文件映射区和栈；堆通常向高地址增长，栈通常向低地址增长。栈由调用过程自动管理，堆由分配器管理，二者都属于虚拟地址空间。

malloc 由用户态分配器决定走空闲块、brk 扩展堆，还是 mmap 建立匿名映射；阈值受实现和运行时调优影响，不能死记某个固定字节数。mmap 还可用于文件映射、共享库和共享内存。

内存不足时，内核先尝试回收干净文件页、写回脏页或换出匿名页；后台回收和直接回收仍不足时，可能触发 OOM Killer。应用侧应限制缓存、检查泄漏和峰值，而不是只调大虚拟地址空间。

**Key words:** 代码段、数据段、BSS、堆、栈、malloc、brk、mmap、文件页、匿名页、Swap、OOM Killer

### Q11：阻塞 I/O、非阻塞 I/O、多路复用和异步 I/O有什么区别？

**答案：**

- **阻塞 I/O**：调用线程一直等到数据就绪并完成拷贝。
- **非阻塞 I/O**：数据未就绪时立即返回，应用需要再次尝试，单独轮询容易浪费 CPU。
- **I/O 多路复用**：select、poll、epoll 等一次等待多个文件描述符的就绪事件，再对就绪 fd 读写；它解决的是“等多个 I/O”，不等同于内核替应用完成数据拷贝。
- **信号驱动 I/O**：就绪时通过信号通知。
- **异步 I/O**：提交请求后立即返回，由内核完成数据搬运并回调/通知。

高并发网络服务常使用非阻塞 Socket + epoll + 事件循环；CPU 密集或可能阻塞的业务放入线程池。

**Key words:** 阻塞 I/O、非阻塞 I/O、I/O 多路复用、异步 I/O、文件描述符、事件循环

### Q12：select、poll、epoll 有什么区别？边缘触发如何避免丢事件？

**答案：**

| 维度 | select | poll | epoll |
| --- | --- | --- | --- |
| 关注集合 | 位图，受实现的 fd 上限影响 | 动态数组 | 内核对象保存关注集合 |
| 返回方式 | 每次遍历关注集合 | 每次遍历关注集合 | 返回就绪事件集合 |
| 常见成本 | O(n) 扫描和用户/内核拷贝 | O(n) 扫描和拷贝 | 通常与就绪事件数更相关 |
| 使用特点 | 兼容性好 | 无固定 1024 限制 | 适合大量连接和事件驱动 |

**水平触发（LT）**只要条件仍满足就持续通知，容易写但可能重复唤醒；**边缘触发（ET）**只在状态变化时通知，必须把 fd 设为非阻塞并循环读写到 EAGAIN，否则未处理的数据不会再次提醒。ET 的性能收益来自减少通知，不代表业务处理自动变快。

**Key words:** select、poll、epoll、O(n)、就绪事件、LT、ET、非阻塞、EAGAIN、C10K

### Q13：什么是零拷贝？它为什么能提升网络服务性能？

**答案：**

传统“读文件再写 Socket”可能经历磁盘到内核、内核到用户、用户回内核、内核到网卡等多次搬运和上下文切换。sendfile、splice、mmap 等机制可以让数据尽量留在内核态，减少用户态参与、拷贝次数和切换次数。

“零拷贝”不是所有平台都严格零次复制；网卡/磁盘 DMA、页引用、TLS 加密都会影响实际路径。它最适合静态文件、日志转发和消息转发，不适合需要在用户态修改每个字节的场景。

**Key words:** 零拷贝、sendfile、splice、mmap、DMA、上下文切换、内核态、静态文件

### Q14：高并发服务器为什么常用“epoll + 线程池”？Socket 的连接队列是什么？

**答案：**

每请求一个进程/线程模型直观，但连接数上升后会消耗栈、调度和上下文切换资源。事件循环用 epoll 监听大量 Socket，只有就绪时才处理；CPU 密集或阻塞任务交给有界线程池，避免事件循环被拖住。

TCP 监听 Socket 维护：

- **半连接队列**：收到 SYN、尚未完成握手的连接。
- **全连接队列**：三次握手完成、等待应用 accept 的连接。

accept 从全连接队列取出连接并返回新的文件描述符；监听 fd 只负责接收新连接，已连接 fd 负责收发数据。队列满、线程池耗尽或应用不及时 accept 都会表现为连接超时或拒绝。

**Key words:** epoll、事件循环、线程池、监听 Socket、半连接队列、全连接队列、accept、文件描述符

## 三、从 Socket 到 TCP/IP

### Q15：OSI 七层模型和 TCP/IP 模型如何对应？一次发送经历了什么封装？

**答案：**

面试中可按 TCP/IP 四层回答：**应用层**（HTTP、DNS、RPC）、**传输层**（TCP、UDP）、**网际层**（IP、ICMP）、**网络接口层**（以太网、Wi-Fi、ARP）。OSI 的表示层、会话层通常并入 TCP/IP 应用层。

发送时应用数据依次加上 TCP/UDP 头形成报文段、加 IP 头形成数据包、再加链路层头尾形成帧；接收端反向解封装。端口标识主机内的进程，IP 负责跨网络寻址，MAC 负责当前链路转发。

**Key words:** OSI、TCP/IP、应用层、传输层、IP、链路层、封装、解封装、端口、MAC

### Q16：从浏览器输入一个 HTTPS 地址到页面显示，中间发生了什么？

**答案：**

1. 浏览器解析 URL，并检查浏览器、系统和代理缓存；域名未命中时通过 hosts 和 DNS 获取 IP。
2. 判断目标是否在本地子网，必要时用 ARP/邻居发现获得下一跳 MAC；通过 Socket 发起 TCP 连接。
3. TCP 三次握手建立可靠字节流；HTTPS 再进行 TLS 握手，校验证书并协商会话密钥。
4. 浏览器发送 HTTP 请求，网卡中断、内核协议栈和 epoll 把数据交给服务端；Nginx/网关可能先做 TLS 终止、限流和负载均衡。
5. 应用读取请求、访问缓存/数据库并返回响应；浏览器按状态码、缓存头和内容类型处理 HTML，再递归加载 CSS、JS、图片等资源。

这个过程可以按 DNS、TCP、TLS、HTTP、服务端处理、渲染六段定位延迟。

**Key words:** URL、hosts、DNS、ARP、Socket、TCP、TLS、HTTP、Nginx、缓存、浏览器渲染

### Q17：TCP 头部有哪些关键字段？它如何保证可靠传输？

**答案：**

TCP 头部关注源/目的端口、序列号、确认号、数据偏移、标志位、窗口、校验和和选项。序列号标识字节位置，确认号表示下一个期望字节；SYN 建连，ACK 确认，FIN 关闭，RST 强制重置。

可靠性来自**按序字节流、累计确认、超时/快速重传、校验和、接收窗口流量控制和拥塞控制**。发送窗口通常受 min(接收窗口 rwnd、拥塞窗口 cwnd) 限制。TCP 只保证传输层可靠，不保证应用业务一定成功。

**Key words:** TCP 头部、序列号、确认号、SYN、ACK、FIN、RST、校验和、重传、rwnd、cwnd

### Q18：TCP 三次握手为什么是三次？服务端收到 SYN 后做什么？

**答案：**

1. 客户端发送 SYN，携带自己的初始序列号，进入 SYN-SENT。
2. 服务端回复 SYN+ACK，确认客户端序列号并发送自己的序列号，进入 SYN-RECEIVED。
3. 客户端发送 ACK，双方进入 ESTABLISHED；第三次 ACK 可以携带应用数据。

三次是为了让双方都确认“我能发、我能收、对方能收”，同步两个初始序列号，并降低历史重复 SYN 造成错误连接的风险。服务端收到 SYN 后创建传输控制块、放入半连接队列并发送 SYN+ACK；第三次 ACK 到达后进入全连接队列，accept 再取走它。两次握手不能同时完成双方序列号确认，也更容易留下无效连接。

**Key words:** 三次握手、SYN、SYN-ACK、ACK、ISN、SYN-SENT、SYN-RECEIVED、半连接队列、accept

### Q19：握手报文丢失或收到大量 SYN 时会怎样？

**答案：**

- 第一个 SYN 丢失：客户端超时重传 SYN。
- SYN+ACK 丢失：客户端重传 SYN，服务端在超时后重传 SYN+ACK。
- 第三个 ACK 丢失：客户端通常已进入 ESTABLISHED，服务端仍在 SYN-RECEIVED，会重传 SYN+ACK；客户端再次 ACK 后完成。
- 大量伪造 SYN 会填满半连接队列，形成 **SYN Flood**。可结合 SYN Cookies、合理队列长度、限速、负载均衡、清洗服务和监控保护。

重传次数和退避时间由操作系统配置决定，不应把某个发行版默认值当作协议保证。

**Key words:** 超时重传、指数退避、SYN Flood、半连接队列、SYN Cookies、限速、队列溢出

### Q20：TCP 四次挥手为什么通常需要四步？TIME_WAIT 有什么用？

**答案：**

关闭是双方独立关闭发送方向的过程：

1. 主动关闭方发送 FIN，表示自己不再发送。
2. 被动关闭方立即 ACK，但仍可继续发送剩余数据。
3. 被动关闭方发送自己的 FIN。
4. 主动关闭方 ACK，进入 TIME_WAIT，等待一段时间后 CLOSED。

ACK 和 FIN 不能总合并，因为被动方收到 FIN 时应用可能还有数据；若没有数据并满足实现条件，也可能出现 FIN+ACK 的“三次挥手”。TIME_WAIT 通常持续 2MSL：既给最后 ACK 丢失后的 FIN 重传留时间，也避免旧报文污染新连接。大量 TIME_WAIT 要先判断谁主动关闭、是否禁用 Keep-Alive，再考虑端口和连接复用。

**Key words:** 四次挥手、FIN、ACK、半关闭、CLOSE_WAIT、FIN_WAIT、TIME_WAIT、2MSL、Keep-Alive

### Q21：流量控制、拥塞控制和超时重传分别解决什么问题？

**答案：**

- **流量控制**面对接收方处理能力，用接收窗口 rwnd 防止发送方把接收缓冲区打满。
- **拥塞控制**面对网络承载能力，用拥塞窗口 cwnd 控制注入网络的数据量；典型阶段包括慢启动、拥塞避免、快速重传和快速恢复。
- **超时重传/快速重传**处理丢包，发送方根据 ACK、重复 ACK 和 RTT 估计决定是否重发。

因此实际发送窗口受两者共同约束：send window = min(rwnd, cwnd)。应用层重试要有幂等设计和退避，否则会在 TCP 已经重传的基础上放大流量。

**Key words:** 流量控制、拥塞控制、rwnd、cwnd、慢启动、拥塞避免、快速重传、RTT、退避、幂等

### Q22：TCP 为什么会粘包？应用协议如何解决消息边界？

**答案：**

TCP 是可靠的**字节流**，只保证顺序，不保留发送方 write 的消息边界。一次 read 可能读到半条、整条或多条消息，这不是 TCP 丢包。

应用协议必须自行 framing，常见方案是：

- 固定长度；
- 分隔符，例如 HTTP 头部的 CRLF；
- “长度字段 + payload”；
- 使用带边界的报文协议，例如 UDP，但仍要自己处理丢包和乱序。

解析器要校验长度上限、处理半包、多包和恶意超长输入。

**Key words:** TCP 字节流、粘包、拆包、半包、消息边界、Content-Length、分隔符、长度前缀

### Q23：TCP 和 UDP 怎么选？UDP 上如何承载 HTTP/3？

**答案：**

TCP 面向连接，提供有序可靠字节流、流量控制和拥塞控制，适合大多数 Web、数据库和 RPC；UDP 无连接、报文有边界、头部小、支持一对多，但默认不保证送达、顺序或去重。

HTTP/3 使用基于 UDP 的 **QUIC**：在用户态实现连接 ID、可靠流、重传、拥塞控制、TLS 1.3 和连接迁移。它减少 TCP/TLS 建连时延，并把不同流隔离，避免一个 TCP 字节流丢包阻塞所有 HTTP/2 流；但仍受带宽、CPU 和网络丢包影响。

**Key words:** TCP、UDP、可靠性、报文边界、QUIC、HTTP/3、TLS 1.3、连接迁移、多路复用

## 四、应用层协议与安全

### Q24：HTTP 请求/响应由什么组成？常见状态码如何定位问题？

**答案：**

请求由请求行、请求头、空行和可选请求体组成；响应由状态行、响应头、空行和响应体组成。头部描述 Host、内容类型、长度、缓存、认证和连接策略。

状态码按首位分为 1xx 提示、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误。高频状态码：200 成功，201 创建，204 无内容，206 范围响应，301/302 重定向，304 未修改，400 参数错误，401 未认证，403 无权限，404 不存在，429 限流，500 应用异常，502 上游响应无效，503 服务不可用，504 上游超时。

502 更偏“网关拿到了无效上游响应”，504 更偏“网关等待上游超时”，最终仍需结合网关和上游日志。

**Key words:** 请求行、响应行、Header、Body、2xx、3xx、4xx、5xx、304、429、502、504

### Q25：GET、POST、PUT、DELETE 的语义、安全性和幂等性如何区分？

**答案：**

- GET 获取资源，规范上安全且幂等，参数常在 URL；不要依赖 GET 修改服务端状态。
- POST 提交或创建资源，通常非安全、非幂等；重试支付、下单等操作必须使用业务幂等键。
- PUT 以目标 URI 的完整表示更新或创建，规范上幂等。
- DELETE 删除目标资源，规范上幂等，但具体业务仍可能产生副作用。
- HEAD 只取响应头；OPTIONS 常用于能力探测和 CORS 预检。

“幂等”表示同一请求执行多次的最终效果相同，不表示每次都没有网络或日志副作用。

**Key words:** GET、POST、PUT、DELETE、HEAD、OPTIONS、安全方法、幂等性、幂等键、CORS

### Q26：HTTP/1.1 长连接、消息 framing、HTTP/2 和 HTTP/3 有什么关系？

**答案：**

HTTP/1.1 Keep-Alive 在一条 TCP 连接上复用多个请求，减少握手开销；请求体可由 Content-Length 或 chunked framing 确定边界。HTTP/1.1 管线化受 TCP 队头阻塞影响，实践中常用并发连接。

HTTP/2 用二进制帧、HPACK/QPACK 类头部压缩和多路复用，把多个 Stream 放入一条 TCP 连接，缓解应用层队头阻塞，但 TCP 丢包仍会阻塞整条连接。HTTP/3 把 HTTP 映射到 QUIC 的独立流，进一步降低丢包影响。

协议升级不等于服务一定更快，还要看连接复用、拥塞、压缩、代理兼容和服务端实现。

**Key words:** Keep-Alive、Content-Length、chunked、HTTP/1.1、HTTP/2、HTTP/3、二进制帧、多路复用、队头阻塞

### Q27：HTTP 为什么不安全？HTTPS/TLS 如何防窃听和中间人？

**答案：**

HTTP 本身是明文，链路上的攻击者可以窃听、篡改或冒充。HTTPS = HTTP over TLS，先完成 TCP（或 QUIC）连接，再进行 TLS 握手：

1. ClientHello/ServerHello 协商版本、随机数和密码套件；
2. 服务端发送证书链，客户端校验域名、有效期、签发链和用途；
3. 双方通过 ECDHE 等密钥交换得到共享密钥，后续用对称加密保护数据；
4. Finished 校验握手未被篡改，之后发送加密 HTTP。

TLS 1.2 常见为 1-2 RTT，TLS 1.3 通常 1-RTT，恢复连接可 0-RTT；证书主要解决身份认证，不能单独防止终端被攻陷。JWT 的签名也不等于加密，不能把敏感明文直接放进 payload。

**Key words:** HTTP 明文、HTTPS、TLS、CA、证书链、域名校验、ECDHE、对称加密、前向保密、中间人

### Q28：DNS 是怎么解析的？为什么通常 UDP，什么时候用 TCP？

**答案：**

客户端先查浏览器/系统缓存和 hosts，再向递归 DNS 查询；递归服务器无缓存时依次询问根、顶级域和权威服务器，得到记录后按 TTL 缓存。A/AAAA 记录返回地址，CNAME 表示别名，NXDOMAIN 表示域名不存在。

普通查询通常使用 UDP 53，低开销且一次请求一个报文；响应过大、被截断、区域传送 AXFR 或特定实现会改用 TCP 53。DNS 失败要区分“域名不存在、解析超时、返回错误 IP、缓存未刷新和应用连不上 IP”。

hosts 可用于本地测试，但它绕过公共 DNS，改动后要注意缓存和权限。

**Key words:** DNS、递归、根服务器、TLD、权威 DNS、A/AAAA、CNAME、TTL、UDP 53、TCP 53、hosts

### Q29：Cookie、Session、Token 和 JWT 如何选？Cookie 被禁用怎么办？

**答案：**

- HTTP 协议本身无状态；Cookie 是浏览器保存并按规则自动携带的小片段数据。
- Session 把状态放服务端，客户端通常只保存 Session ID；集群需要共享存储、粘性会话或集中式 Session。
- Token 把身份凭证交给客户端，请求时通过 Authorization 等头部发送；JWT 由 Header、Payload、Signature 组成，默认只签名不加密。
- Cookie 可设置 Secure、HttpOnly、SameSite 和过期时间；localStorage 容量较大但会被同源脚本读取，不能因为“不是 Cookie”就认为更安全。

Cookie 被禁用时，Session 可用 URL 重写或隐藏字段传递 ID，但容易泄露且体验差；更常见的是使用 Authorization Token，并配合短过期、刷新令牌、撤销列表、轮换和最小权限。

**Key words:** 无状态、Cookie、Session、Session ID、Token、JWT、HttpOnly、Secure、SameSite、localStorage、刷新令牌

### Q30：HTTP 长连接、WebSocket 和 SSE 怎么选？为什么 Agent 常用 SSE？

**答案：**

- **HTTP Keep-Alive** 仍是请求-响应模型，只是复用连接。
- **WebSocket** 通过 HTTP Upgrade 建立全双工长连接，适合聊天、协作、行情等双向高频交互。
- **SSE** 基于 HTTP 的 text/event-stream，服务端单向持续推送，浏览器通常自动重连，适合模型 token、任务进度和日志流。

SSE 实现轻、易接入 HTTP 代理，特别适合“用户发起一次请求，服务端持续输出”；需要客户端和服务端都频繁发送消息时再选 WebSocket。流式接口要设计事件类型、序号、心跳、取消、超时和断线恢复，不能把每个 chunk 当作完整业务消息。

**Key words:** Keep-Alive、WebSocket、Upgrade、SSE、text/event-stream、全双工、单向推送、心跳、断线恢复

### Q31：RPC、HTTP、MCP、ACP/A2A 分别解决什么问题？

**答案：**

HTTP 是通用应用层协议；RPC 更像“调用方式和接口约定”，让调用方以本地方法形式调用远端服务，常见实现有 gRPC、Thrift，内部服务可用二进制协议和 IDL 提升性能与类型约束。

在 Agent 系统中：

- **Tool Calling** 解决一次模型到业务函数的调用；
- **MCP** 更强调以统一协议发现和接入工具、资源、上下文，传输可落在 stdio、HTTP 或 SSE 上；
- **ACP/A2A** 更偏多个 Agent 之间交换任务、能力、消息和状态。

它们不是 TCP/HTTP 的替代品，而是建立在传输承载之上的应用协议或交互约定。

**Key words:** HTTP、RPC、gRPC、IDL、Tool Calling、MCP、stdio、SSE、ACP、A2A、能力发现

### Q32：Nginx 反向代理和负载均衡如何工作？

**答案：**

Nginx 作为 HTTP 反向代理工作在应用层，也可以通过 stream 模块做四层 TCP/UDP 转发。它接收客户端连接，再把请求转发给后端，并可完成 TLS 终止、静态文件、缓存、限流、健康检查和连接复用。

常见算法有轮询、加权轮询、最少连接、IP/URL 哈希；会话需要保持时才使用哈希或把 Session 放到共享存储。502 常检查上游返回和协议，504 常检查上游处理耗时、连接池和超时配置；代理超时不能替代应用级取消和重试策略。

**Key words:** Nginx、反向代理、四层、七层、轮询、加权、最少连接、IP 哈希、TLS 终止、502、504

## 五、综合排障与场景题

### Q33：网页一直转圈，如何按层定位？

**答案：**

按“客户端 → DNS → 链路 → TCP/TLS → HTTP → 应用依赖 → 浏览器渲染”逐层缩小范围：

1. 浏览器开发者工具看 DNS、连接、TLS、首字节和下载耗时；确认是否只是前端脚本卡住。
2. 检查域名是否解析、TTL 是否过期、hosts/代理是否异常；必要时对比不同 DNS。
3. 检查本机网络、路由、防火墙、丢包和 MTU；ping 不通不等于 TCP 不通。
4. 检查 TCP 三次握手、重传、连接池、TLS 证书和握手耗时。
5. 根据 HTTP 状态码和响应头定位网关、认证、缓存或应用问题；504 重点看上游耗时。
6. 关联服务日志、数据库/缓存慢查询、线程池、CPU、内存、GC、负载和 trace，判断是排队还是执行慢。

排障要记录时间窗口、请求 ID、客户端/服务端观测点，避免只凭“重启后好了”下结论。

**Key words:** DNS、路由、丢包、MTU、TCP 握手、TLS、首字节、HTTP 状态码、线程池、慢查询、trace

### Q34：服务端显示启动成功，但客户端请求不到，怎么排查？

**答案：**

按顺序检查：

- 服务是否监听了正确的 IP 和端口，是否只绑定 127.0.0.1；确认 IPv4/IPv6 是否匹配。
- 本机端口是否被防火墙、安全组、容器网络或代理拦截；客户端是否走了错误代理。
- DNS 是否指向旧地址，负载均衡健康检查是否把实例摘除。
- TCP 是否能建立；能建立后再区分 TLS 证书、HTTP 路径、认证和业务错误。
- 读取网关、服务端和内核连接状态；连接建立但无响应时重点看线程池、事件循环和上游依赖。

HTTP 400/401/403/404/500/502/503/504 分别指向参数、身份、权限、路由、应用、网关和可用性问题，但必须结合日志确认。

**Key words:** bind、listen、端口、127.0.0.1、IPv4/IPv6、防火墙、安全组、DNS、健康检查、状态码

### Q35：两台服务器如何判断连接是否正常？TCP KeepAlive 和应用心跳有什么差异？

**答案：**

先用 DNS/IP、路由和端口连通性验证“能否建立新连接”，再用应用请求验证“协议和业务可用”。已建立但长期空闲的连接，可开启 TCP KeepAlive 探测对端是否仍存在；它通常由 keepalive_time、keepalive_intvl、keepalive_probes 控制，发现故障可能较慢。

应用层心跳可以携带连接 ID、版本和业务状态，按更短间隔探测并及时摘除实例，但需要处理误判、重连风暴和幂等。生产环境常结合 TCP KeepAlive、应用心跳、连接超时和服务发现健康检查。

**Key words:** TCP KeepAlive、SO_KEEPALIVE、心跳、连接超时、重连、健康检查、服务发现、故障摘除

### Q36：服务器 ping 不通但 HTTP 能成功吗？为什么？

**答案：**

可以。ping 使用 ICMP Echo，HTTP 通常使用 TCP 80/443；防火墙、安全组或云厂商策略可以禁止 ICMP、只开放 TCP 端口。因此 ping 失败只能说明 ICMP 路径或策略异常，不能直接证明 Web 服务不可用。

反过来，ping 成功也不能证明应用健康：应用端口可能未监听、TLS 失败、网关返回 503，或业务处理超时。连通性排查应分别测试 ICMP、TCP、TLS、HTTP 和业务接口。

**Key words:** ICMP、ping、TCP、HTTP、80/443、防火墙、安全组、连通性、应用健康

### Q37：DDoS、SYN Flood、SQL 注入、XSS、CSRF 和 DNS 劫持如何防护？

**答案：**

- **DDoS/SYN Flood**：在网络层、传输层和应用层分别做清洗、CDN/负载均衡、限速、SYN Cookies、连接和请求配额；容量扩展只能缓解，不能代替检测。
- **SQL 注入**：参数化查询/预编译、输入校验、最小数据库权限，避免拼接 SQL。
- **XSS**：上下文相关输出编码、输入校验、CSP、避免危险 DOM API；敏感 Cookie 设置 HttpOnly。
- **CSRF**：SameSite Cookie、CSRF Token、校验 Origin/Referer，并对关键操作二次确认。
- **DNS 劫持**：使用可信解析、DNSSEC/DoH 等能力，校验 HTTPS 证书和域名，检查异常 hosts 与解析变更。

安全控制要和日志、告警、密钥轮换及应急撤销结合，不能只依赖一项配置。

**Key words:** DDoS、SYN Flood、SYN Cookies、限流、SQL 注入、参数化查询、XSS、CSP、CSRF、SameSite、DNSSEC

### Q38：如何把操作系统和网络知识串成一个服务端设计答案？

**答案：**

可以按以下链路回答一个高并发 HTTP 服务：

1. 进程提供资源隔离，线程/协程提供并发执行；共享状态用锁、原子操作或消息队列保护。
2. Socket 是文件描述符，非阻塞 I/O + epoll 负责连接和读写就绪；CPU 密集、磁盘和数据库操作进入有界线程池。
3. 内核通过页表和虚拟内存隔离进程；合理的缓冲区、连接池和零拷贝减少复制与切换。
4. TCP 提供可靠字节流，应用协议自行 framing；TLS 提供身份认证与加密，HTTP 负责语义。
5. Nginx 做接入、TLS 终止、限流和负载均衡；应用通过缓存、数据库和队列完成业务。
6. 用指标、日志、trace 分别观测连接、队列、线程池、内存、依赖耗时和错误码。

这条主线能把“系统调用 → 文件描述符 → epoll → TCP → TLS → HTTP → 业务处理”连起来，比背孤立定义更容易应对追问。

**Key words:** 进程、线程、协程、虚拟内存、Socket、非阻塞、epoll、线程池、TCP、TLS、HTTP、Nginx、可观测性

## 六、一页速刷路线

### 1. 必须能画出来

- 用户态/内核态与系统调用路径；
- 进程、线程、协程和上下文切换；
- 虚拟地址、页表、TLB、缺页异常；
- epoll 事件循环与线程池；
- TCP 三次握手、四次挥手、TIME_WAIT；
- DNS → TCP → TLS → HTTP 的完整请求链路。

### 2. 高频对比题

| 对比 | 记忆主线 |
| --- | --- |
| 进程 vs 线程 | 隔离资源 vs 共享资源 |
| 阻塞 vs 非阻塞 vs 多路复用 | 等待方式不同，数据拷贝仍需处理 |
| LT vs ET | 条件持续通知 vs 状态变化通知 |
| TCP vs UDP | 可靠字节流 vs 轻量报文 |
| HTTP/1.1 vs HTTP/2 vs HTTP/3 | 文本/连接复用 vs 帧/多路复用 vs QUIC 独立流 |
| Cookie/Session/Token/JWT | 状态放哪里、如何携带、如何撤销 |
| SSE vs WebSocket | 单向 HTTP 流 vs 双向实时连接 |

### 3. 面试回答模板

先给一句结论，再按“工作流程 → 为什么这样设计 → 异常/边界 → 实际场景”展开，最后用本题 **Key words** 复盘。涉及性能时同时说明 CPU、内存、网络、锁和可观测性，避免只回答单一层次。
