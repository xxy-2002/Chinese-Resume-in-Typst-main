# Meta-Harness 参考笔记

这份笔记记录的是 **Meta-Harness** 这类方向给你的启发。

定位：

- 外部相关工作参考
- 方法论参考
- 不替代你自己的项目事实

## 一、它为什么有意思

Meta-Harness 这类工作最打动人的地方，不是“又一个 Agent 框架”，而是它把一个很关键的问题说清楚了：

> 当你要让一个 Agent 去优化另一个 Agent，最重要的输入不只是分数，而是完整的执行证据。

换句话说，它强调：

- 诊断要看原始轨迹
- 优化要基于证据
- 不是只看总分就决定怎么改

## 二、它最值得吸收的点

### 1. Trace 比摘要更重要

这类工作里的核心判断是：

- 给模型一个模糊摘要，不足以做高质量诊断
- 给它完整执行轨迹、工具调用记录和中间状态，效果更好

这和你现在的资料体系高度相关，因为你已经在准备：

- `Trace`
- `Eval`
- `GEPA`
- `Skill Factory`

### 2. Proposer 不该盲改

Meta-Harness 这类思路背后有一个非常重要的工程原则：

- 优化器不能拍脑袋改
- 先看失败轨迹
- 再做失败归因
- 再提出候选修改

这和你现在在 `Skill Factory` 里讲的：

- `trace 驱动`
- `候选生成`
- `多目标筛选`

是一路的。

### 3. Harness 是优化闭环的承载体

它不是只把 harness 当执行壳，而是把 harness 当作：

- 运行证据的采集器
- 评测链路的承载体
- 候选改动的验证环境

这和你自己的项目表述也很容易对上：

- `JoyDeliver`：`Harness Agent + Runtime`
- `Skill Factory`：可插拔 `Harness`

## 三、和你当前准备的连接方式

### 和 Skill Factory 的连接

这是最强的一条线：

- `Skill Factory` 里你讲 `trace`、`sandbox`、`GEPA`
- Meta-Harness 正好强化“优化前必须看轨迹证据”

所以你可以把它当成一种外部方法论支持：

- 你的项目不是只在做 prompt 调优
- 而是在做基于执行轨迹的工程化优化闭环

### 和 Flow 的连接

- 评估流水线
- 记忆与执行轨迹
- 工具调用过程诊断

### 和 JoyDeliver 的连接

- 长链路任务流
- Trace 记录
- 可观测性与可复现性

## 四、面试里怎么提它

建议表达：

“我自己在项目里会比较重视 trace 和评测闭环。看外部相关工作时，像 Meta-Harness 这类方向让我印象比较深，因为它强调优化 Agent 时最重要的不是只看分数，而是看原始执行轨迹，这和我在 Skill Factory 里关注的 trace 驱动优化思路是很一致的。”

## 五、它适合放在哪个优先级

建议定位：

- `C 级参考`
- 方法参考
- 不要抢主线时间

主线还是：

- `JoyDeliver`
- `Flow`
- `Skill Factory`
- `Redis / MySQL / 网络`
- `Agent 基础概念`

## 六、一句话总结

“Meta-Harness 最值得学的，是它把 `trace-first diagnosis` 讲清楚了：先看轨迹，再做归因，再做优化。”
