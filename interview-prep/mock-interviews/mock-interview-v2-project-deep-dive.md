# 模拟面试稿 V2：项目深挖版

这版更偏 `商业智能 / 决策支持` 背景下的 AI 平台 / Agent 工程岗位，重点深挖 `JoyDeliver`、`Flow`、`Skill Factory`。

## 1. 你做的三个核心项目之间有什么统一主线

答：

“统一主线是：让 Agent 系统从能跑，走到可复用、可评测、可观测、可优化。JoyDeliver 偏交付流程平台化，Flow 偏多模型、多 Agent 和记忆治理，Skill Factory 偏 Skill 资产化和闭环优化。”

纵向追问：

- 为什么你一直在做平台层而不是单应用层

横向追问：

- 你觉得这三者里最难的是哪块

## 2. JoyDeliver 为什么要抽象 Agent / Skill / Pipeline 三层

答：

“因为它们解决的问题不一样。Agent 更偏执行者，Skill 更偏可复用能力单元，Pipeline 更偏业务流程编排。如果三者不拆开，平台很容易在业务增长后变成一堆 hardcode 流程。”

纵向追问：

- 如果只保留 Agent 行不行
- Skill 是怎么复用的

横向追问：

- 这个抽象和 Flow 里的 Agent 治理有什么共性

## 3. Flow 的记忆架构最难的点是什么

答：

“最难的不是把记忆存下来，而是在多 Agent 并发下同时保证共享效率、逻辑隔离和一致性。因为一旦只共享不隔离，就会污染；只隔离不共享，又失去协同价值。”

纵向追问：

- Cortex 是怎么理解的
- MemoryBuffer 在里面是什么角色

横向追问：

- 这和 RAG 里的长短期记忆有什么关系

## 4. 为什么你们要做无状态 Validator

答：

“因为 Validator 的核心职责是校验，不应该自己带额外业务状态。无状态更容易复用、扩展和并发部署，也更容易把问题收敛到输入输出正确性上。”

纵向追问：

- 它主要校验什么

横向追问：

## 5. Skill Factory 里你为什么强调 trace

答：

“因为只看总分你不知道为什么错。Trace 把执行过程、工具调用、中间状态和结果都记录下来，下一轮优化才能基于证据改，而不是拍脑袋改。”

纵向追问：

- 具体记录哪些字段
- 如何控制 trace 成本

横向追问：

- 这和你在 JoyDeliver 里做 trace 的思路一致吗

## 6. 你怎么理解 GEPA 在项目里的作用

答：

“我理解它不是一个单点技巧，而是一种候选生成和选优思路。先基于轨迹和 badcase 生成新候选，再通过多指标比较保留更优方案，而不是靠一次 prompt 改动就拍板。”

纵向追问：

- 为什么还需要 Pareto Frontier

横向追问：

- 它和普通网格搜索、人工调 prompt 的区别是什么

## 7. 5 维 AND 门控为什么比加权分更好

答：

“因为加权分可能允许一个维度大涨去掩盖另一个维度退化。工程里很多时候不能这样，比如成功率涨了但成本翻倍、或者 dev 变好了但 regression 坏了。AND 门控更像硬约束。”

## 8. 你怎么看 Skill 更像 Harness 这句话

答：

“因为真正可用的 Skill 已经不只是写几段 prompt 了，它要处理触发边界、安全规则、参考资料一致性、脚本兼容、回归验证。这些东西加起来更像一套小型执行系统。”

## 9. 如果让你现在再重做 Skill Factory，你会优先补什么

答：

“我会优先补两块，一块是评测数据和分层回归体系，一块是 trace 到诊断建议的自动化衔接。因为前者决定能不能稳定衡量，后者决定能不能高效迭代。”

## 10. 如果这个岗位偏商业智能和决策支持，你觉得你的经历哪里最匹配

答：

“我觉得最匹配的是两点。第一，我做的不是泛聊天型 Agent，而是面向真实业务流程的结构化任务系统，比如交付流程、问答、可行性分析、标书和 PPT 生成，这和业务决策支持更接近。第二，我一直比较重视 eval、trace、路由和稳定性，这些对商业智能类应用很关键，因为这类系统不能只会生成，还要可验证、可解释、可持续优化。”
