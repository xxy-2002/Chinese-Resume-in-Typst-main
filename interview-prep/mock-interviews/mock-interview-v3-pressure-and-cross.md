# 模拟面试稿 V3：压力追问与横向对比版

这版更像 `AI应用研发工程师` 的强追问场景，重点是纵向压细节、横向做比较，并贴近 `商业智能&决策支持` 语境。

## 1. 你说自己做 Agent 平台，和市面上的东西相比到底新在哪

答：

“我不会把它讲成发明了一个全新范式，而是更强调在具体业务场景下的工程落地。像 JoyDeliver 侧重交付流程结构化和经验复用，Flow 侧重模型接入、记忆、路由和评估闭环，Skill Factory 侧重 Skill 资产化和自优化。新意更多在工程抽象和闭环设计上，而不是单个 buzzword。”

追问：

- 所以你和 Dify 的核心差别是什么
- 和 Coze 的差别是什么
- 如果用 LangGraph 能不能做

## 2. 你简历里写了很多概念，哪些是你真的做过，哪些只是理解过

答：

“我会严格区分。像 JoyDeliver 的 Harness Agent、Runtime、Skill/Pipeline 编排，Flow 的 Model Adapter、Cortex、Validator、评估流水线、TOON 和语义压缩，这些是我可以按职责和价值展开的。像 aboutskill 里那套更完整的 skill-evolver 叙事，我会把它当相关工作和方法参考，而不是直接当作简历事实。”

追问：

- 那你怎么证明自己不是只会讲概念

## 3. 你为什么觉得 Harness 是更好的表述，而不是继续说框架

答：

“因为框架这个词太宽了，容易只让人想到 SDK 或编排层。Harness 更强调模型外的执行基座，包括工作区、工具、状态、trace、eval、sandbox 和 guardrail，这更接近我实际做的事情。”

## 4. 你说 Trace 很重要，那没有 Trace 能不能优化

答：

“也能，但大概率效率更低，而且诊断会更模糊。没有 trace，很多时候只能看总分或者最终输出猜问题；有 trace，才能知道具体是路由错了、工具参数错了、还是上下文污染了。”

追问：

- 既然 trace 这么好，为什么不把所有 trace 全喂给模型

## 5. 你在 Flow 里用了 Redis + Lua，为什么不用数据库锁

答：

“因为我们面对的是高并发、跨实例协调和轻量共享资源控制，Redis 在这类场景下更合适。Lua 的价值是把判断和更新合成原子操作，减少竞态窗口。数据库锁更适合事务性强、数据一致性要求极高但吞吐要求没那么激进的场景。”

横向追问：

- 那如果 Redis 挂了怎么办
- Redis 锁有什么坑

## 6. 你 Skill Factory 里为什么要分 dev / holdout / regression

答：

“因为只看 dev 很容易在开发集上变好但泛化没变好，或者把老 case 弄坏。holdout 是看泛化，regression 是防止历史能力退化。”

追问：

- 如果只能保留一套，你保留哪套

## 7. 你写了 Go、Python、C++，哪门语言最能代表你

答：

“从当前简历经历的贴合度来看，Python 最能代表我，因为我做的大模型应用、FastAPI、评估链路和很多 Agent 工程都直接用到了它。Go 我会讲并发和工程结构，C++ 我会控制在 STL/Asio 和基础工程理解的范围内。”

## 8. 你最担心面试官从哪里把你问穿

答：

“我更警惕的是把平台化概念问到实现边界，比如 Runtime 到底管什么、trace 到底记录什么、eval 到底怎么分层。因为这些问题不能只靠大词回答，必须落到具体职责。”

## 9. 如果今天只让你选一个最能代表你的项目

答：

“我会选 Skill Factory。因为它把我前面几段经历中接触到的 Agent、Skill、评测、trace、优化闭环这些东西都收束到一个统一对象上，既能讲工程抽象，也能讲执行闭环，还能讲验证与选优。”

## 10. 商业智能和决策支持场景里，为什么 Agent 不能只追求生成效果

答：

“因为这类场景更看重结构化正确性、流程稳定性和可验证性。很多时候问题不是模型会不会说，而是有没有选对工具、有没有走对流程、输出是不是可落库、可复核、可回归。所以比起单纯生成质量，我会更强调 trace、eval、guardrail 和 workflow 稳定性。”
